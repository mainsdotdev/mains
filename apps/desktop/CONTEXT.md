# Mains

Shared domain vocabulary for the Mains codebase. Add terms as decisions crystallize during architecture work — keep definitions tight and project-specific.

## Language

### IPC seam

**ServiceResponse**:
The discriminated-union envelope returned by every IPC handler in the main process and unwrapped once by the renderer's base query. Either `{ success: true; data: T }` or `{ success: false; error: string }`. The single canonical shape lives in `@mains/contracts/service-response`, shared with the mobile app; `src/shared/ipc-kit/` keeps a re-export shim. It is a **wire format, not a service return type**: services return plain `T` (or `T | null`) and throw; the envelope is constructed only at the IPC seam by **handle** (or by the few hand-written handlers that need the Electron event). No `dto.ts` re-exports it.
_Avoid_: response, result, envelope, ServiceResult; returning ServiceResponse from a service method; re-exporting it from a module `dto.ts`.

**CHANNELS**:
The single source of truth for IPC channel names, in `@mains/contracts/channels` (`packages/contracts`). Main, preload, and renderer all reference values from this map (e.g. `CHANNELS.account.get`) instead of typing the channel string literally. A typo at any site is a compile-time error and a renamed channel is a single edit. The map is grouped by namespace (the part before the colon) so adding a channel means adding one field to one object.
_Avoid_: channel string literals, magic strings, per-module CHANNELS consts.

**ok / fail**:
The two constructors for a **ServiceResponse**, called almost exclusively by **handle**; the few hand-written handlers (native dialog, terminal streaming, imageProxy signing, localBackend) use them rather than literal objects, so the envelope shape stays in one place.
_Avoid_: success(), error(), wrap(); inline `{ success: false, error }` literals.

**handle**:
The wrapper at the IPC seam (`packages/backend/src/ipc-kit/handle.ts`) that turns a throw-style service function into an `ipcMain.handle` handler: resolved value → `ok(data)`, throw → log + `fail(error.message)`. Every backend `*.ipc.ts` handler uses it except the handful that need the Electron event/invoke context (native dialog, terminal streaming, imageProxy protocol, localBackend), which stay in the desktop host. **Raw-message policy**: the thrown error's message travels to the renderer as-is (local desktop app — debuggability beats leak risk); services throw explicit `Error("Workspace not found")`-style messages where the user should read them.
_Avoid_: try/catch-to-envelope inside service methods; mapping error messages to generic strings inside services.

**absence rule**:
Single-item *reads* return `T | null` — absence is a legitimate state, not an error (a workspace with no diff is not a failure). *Mutations* whose target is missing throw (`"Workspace not found"`). This removes the renderer's "swallow the error into null" transformResponse pattern: null arrives as data.
_Avoid_: `fail("X not found")` from a read; returning null from a mutation that couldn't find its target.

**assertOk / assertFail**:
Generic narrowers for `{ success }` discriminated unions. Service tests no longer need them (throw-style services are asserted with plain values / rejections); their one remaining home is utils-internal result unions such as `parseProviderCredentials` in `connections.utils.ts`. The former `unwrap(r)` helper is **deleted**: `ipcBaseQuery` unwraps the envelope itself, so endpoints write `transformResponse` only to *reshape* data (e.g. project the `resources` key), never to unwrap it.
_Avoid_: expect-success, ok-or-throw, getData; re-introducing an unwrap helper or unwrap-style `transformResponse` (the base query owns unwrapping).

## Relationships

- Every IPC handler returns exactly one **ServiceResponse** (the wire format never changes during the migration).
- A **ServiceResponse** is constructed only via **ok** or **fail**, almost always inside **handle**.
- The renderer unwraps a **ServiceResponse** exactly once, in `ipcBaseQuery` — never in `transformResponse`.
- Services return plain `T` / `T | null` and throw; the **absence rule** decides null-vs-throw.

## Module layout

Each `packages/backend/src/modules/{name}/` domain follows a 6-file layout: `ipc.ts → service.ts → repo.ts → dto.ts → validation.ts → index.ts`. Earlier versions had a `controller.ts` between `ipc.ts` and `service.ts` — it was a pure pass-through across all 26 modules and has been removed. `ipc.ts` calls `service` directly; argument unpacking lives at the ipc call site when needed. Electron-only adapters remain under `apps/desktop/src/main/modules/` and consume the package's public barrels.

A module folder may own **more than one table**. The 6-file layout is per module, not per table. When several tables form one conceptual aggregate (see **workspace** below), they live in one folder under the flat 6-file shape, with each layer's file containing all tables' code.

**Repos are module-internal.** `{name}.repo.ts` is not exported from the module barrel; cross-module access goes through service methods (throw-style, so callers get plain rows) or named barrel functions (`logWorkspaceActivity`, `getConnectionWithSecrets`, `getIssuesByResourceIds`, `recordWorkspaceDiff`). Two exceptions, both deliberate: `workspace.service` imports `projectsRepo` via its file path (not the barrel) to keep the workspace → projects edge acyclic (see **Workspace intake**), and the provider drivers still import `runsRepo`/`workspaceRepo` directly — a known egress-seam leak, to be closed when driver run-I/O is unified behind the run-session seam rather than papered over here.
_Avoid_: re-exporting a repo from `index.ts`; importing another module's repo when a service method or named barrel function exists.

**Seed runner**:
Initial data seeding is *not* a domain module. It lives in `packages/backend/src/db/seeds/` as a versioned, idempotent runner: each `v{N}.ts` exports `run(db)`, the runner tracks `appSettings.seedVersion`, and `db/client.ts` invokes `runSeeds(db)` automatically at database init. The renderer plays no part. There is intentionally no `modules/seed/` — an earlier IPC-driven seed module was vestigial and was removed. Fixtures live in `packages/backend/src/db/data/`; v1.ts imports them.
_Avoid_: re-introducing an `api.seed.*` IPC surface, putting seed code under `db/queries/` (the directory no longer exists), or routing seeding through a domain module. See ADR-0003.

## Aggregate modules

### workspace

The `workspace` module owns five tables: `workspaces`, `workspace_activity`, `workspace_diffs`, `reviews`, `review_findings`. They were previously five separate modules; consolidated because they always travel together (no cross-workspace consumer of the satellites — `pulse` doesn't read them, `stats` joins `workspace_diffs` directly via its own repo, every renderer consumer is workspace-scoped).

IPC channels live under one namespace: `workspace:get*`, `workspace:getActivity`, `workspace:logActivity`, `workspace:getLatestDiff`, `workspace:listReviews`, `workspace:listFindings`, etc. The renderer has one `workspaceApi.ts` with split RTK Query tag types (`Workspace`, `WorkspaceActivity`, `WorkspaceDiff`, `WorkspaceReview`, `WorkspaceFinding`) so UI sections still refresh independently.

Cross-module writers (drivers, run-session, guards, mains-tools) import named functions — `logWorkspaceActivity`, and for diff rows `recordWorkspaceDiff` / `clearWorkspaceDiff` — from the module's barrel, not the full service surface. `recordWorkspaceDiff(workspaceId, runId, snapshot)` owns the `filesJson`/`statsJson` packing and the update-or-insert decision for the latest diff row; it exists because run-session, gitFlow's post-commit recapture, and `resyncDiff` were each hand-rolling the same packing.
_Avoid_: re-splitting into `workspaces` + `workspaceActivity` + `workspaceDiffs` + `reviews` + `reviewFindings` (see ADR-0001); hand-building `statsJson`/`filesJson` outside `recordWorkspaceDiff`.

### connections

The `connections` module owns three tables: `connections`, `connection_tokens`, `connection_states`. They were previously three separate modules; consolidated because the seam between them was already leaking — `connections.service` imported `decryptSecrets` from the credentials utils, `sync/sync.connection-utils.ts` had grown a full duplicate of `getConnectionWithSecrets`, and `connectionStates.service` was a 46-line pass-through. The `connection_resources` table is deliberately *out* of the aggregate; it is read by `projects.repo` directly (same shape as `stats` joining `workspace_diffs`).

IPC channels live under one namespace: the existing `connections:*` channels stay, plus `connections:listStates` and `connections:updateState` (formerly `connectionStates:*`). The renderer has one `connectionsApi.ts` with split RTK Query tag types (`Connection`, `ConnectionState`). The preload collapses to one `window.api.connections` section.

Cross-module readers (`sync`, `guards`) import a single named function — `getConnectionWithSecrets` — from the module's barrel. The crypto helpers (`encryptSecrets`, `decryptSecrets`, `createTokenHash`, `parseProviderCredentials`, `parseConnectionMetadata`) live in `connections.utils.ts` as an internal seam — private to the module, used by its own tests, not re-exported from `index.ts`. Credential rows carry an `encryption_format`, with one current row per connection + format: Electron `safeStorage` and standalone `MNS1` credentials coexist, and each runtime selects only its own current format. Pre-format rows remain `unversioned` and are probed as an upgrade bridge. Reauthorization rotates only the active runtime's format; explicit revoke retires every format.
_Avoid_: re-splitting into `connections` + `connectionStates` + `connectionCredentials`; restoring one global-current credential index that lets Desktop and Server invalidate one another; importing crypto helpers across modules — call `getConnectionWithSecrets` instead. See ADR-0002.

### projects

The `projects` module owns two tables: `projects`, `project_resources`. The latter was previously its own `workspaceResources/` module — a half-finished rename (IPC channels were already `projectResources:*`, the table was already `project_resources`, but the folder and exports still said `workspaceResources`). Consolidated because the seam between them was vestigial: every method on `workspaceResourcesService` took `projectId` as its first argument, the table is FK'd to `projects`, and no caller outside `projects.ipc` ever needed the resource methods without already having a `projectId` in hand. Applying the deletion test: removing `workspaceResources/` concentrated its five methods directly onto `projects.service` with no logic loss.

IPC channels live under one namespace: `projects:list`, `projects:get`, `projects:create`, `projects:update`, `projects:delete`, `projects:archive`, plus the resource channels `projects:listResources`, `projects:listAvailableResources`, `projects:addResource`, `projects:removeResource`, `projects:listIssues`. The pre-merge `projects:getAll` / `projects:getById` channels rename to `projects:list` / `projects:get` to match the workspace style. The renderer has one `projectsApi.ts` with split RTK Query tag types (`Projects`, `ProjectResources`, `ProjectIssues`) so UI sections still refresh independently.

The cross-aggregate query `projects:listIssues` (issues linked to a project via `project_resources` → `connection_resources` → `entities`) is orchestrated at the service layer, not joined at the repo: `projects.service.listIssues()` calls `projects.repo.listLinkedResourceIds(projectId)` and then `getIssuesByResourceIds(resourceIds)` from the `entities/` barrel. Each repo stays scoped to its own tables — same shape as the `getConnectionWithSecrets` seam in **connections**. The `LINKABLE_KINDS` allowlist lives in `projects.utils.ts`.
_Avoid_: re-splitting into `projects` + `projectResources` (or re-introducing `workspaceResources/`). Avoid `projects.repo` importing the `entities` or `issues` schema directly — call `getIssuesByResourceIds` from the entities barrel.

### collections

A **collection** is the account-scoped, non-developer, project-like grouping shared by `work` and `chat` runs. It has no mode, git repository, or workspace identity: a run may belong directly to one collection, while a run with no collection is standalone. The same Collection and Sources appear in Work and Chat, but each sidebar still lists only runs matching its active provider + mode snapshot. The renderer may label collections as “Projects”, but the domain keeps **project** for the git-backed aggregate above. Collection membership is organization and shared context; it does not determine a run's provider session, mode, or working directory.

The module owns `collections` and `collection_sources`. Sources are canonical, immutable context stored under `<userData>/collections/<collectionId>/sources/<sourceId>/`; display names are metadata and never become ownership paths. A workspace-less Work/Chat run with Collection Sources gets one `collection-sources` directory symlink in its own cwd, pointing to the current Collection's canonical `sources` directory. The agent receives a short list of relative paths through the provider's extra-instructions channel where supported. Historical workspace-backed Work/Chat runs receive absolute paths without a link in the workspace. The user's message stays separate and file contents are read only when needed. Runs retain their own cwd for outputs; Collection Source bytes are not copied into it. The file explorer can open, read, and save a copy of an exact registered Collection source file, including through the run symlink; Collection storage is outside its write roots and the rest of the storage tree stays inaccessible. A `run_context` row records source identity, name, and content hash as history. Moving a run updates the symlink without moving its cwd; a follow-up refreshes the source list. Run-local copies written by older builds are left for manual cleanup. Removing a Collection detaches its runs and removes its canonical files.
_Avoid_: attaching workspaces to collections; adding branch/worktree/remote fields to collections; putting work/chat grouping fields on `projects`; moving a run's working directory when its collection membership changes; handing the whole Collections storage root to the file explorer; editing historical run-context rows when Collection Sources change.

### atlas

Atlas access uses the variant descriptor's `supportsAtlas` capability: Claude and Codex can open it; Copilot and Cursor have a disabled rail entry and an unavailable route surface. Saved content remains account-scoped across providers. The first **Start a page** card uses the active provider's icon/name, creates a blank Page and seeds its local chat with `Create a page about ` in the expanded overlay. The user completes and submits that draft; creation never starts an agent run. The starter uses the active provider's Space regardless of its saved mode. The remaining template cards create populated Pages directly; all starter cards use `glass-card`.

Atlas owns a route-local Work experience through `ActiveSpaceOverrideProvider`; it never updates the Space's saved mode or the global active-space selection. Returning Home or to another route therefore retains the user's previous experience. Every supported Page-chat Space is projected to Work locally, so a separate saved Work Space is unnecessary. New-run payloads carry the composer's effective `mode`; the backend validates that mode and provider support, then snapshots it on the run while preserving Space ownership and workspace/collection guards. Omitted modes still use the Space's saved preference, and continuation/fork keep the run's snapshot. A remembered non-Work conversation is never continued as an Atlas Page chat.

Atlas allows document previews (PDF, spreadsheets, Word and text) and a docked browser from the shell's browser icon. Workspace files/changes/activity, session details, subagents and their controls are excluded through the route's workspace-panel gate, including their content insets. Browser expansion is unavailable in Atlas; its saved expansion preference is left intact so leaving Atlas restores the previous browser layout.

**Atlas** is the account-scoped library for native Pages and generated documents/images, independent of the active provider. The shared sidebar owns its All, Pages, Docs and Images navigation, recent Pages, project filters and Trash. The library uses a centered list with Name/Source/Last activity columns, a page-template strip and an image gallery that retains each image's aspect ratio. Category, view, search, project and list/grid selections live in the route query; browser back/forward restores them. The Atlas route publishes multiple Page tabs through the main-header host using the workspace's shared `BaseTab`; opening an existing Page selects its tab, `+` creates a Page, and closing a tab never deletes it. Switching, creating and closing the active tab wait for the editor's save queue. Open tabs and each Page's working-chat draft, run and overlay mode live as session state in `atlasSlice`, isolated by backend/account. Page chats reuse `FloatingChatOverlay` and `useWorkspaceRuns` with local selection, so conversation history, streaming, approvals and continuation stay inside the Page without changing workspace tabs. Generated files are a bounded projection of registered run artifacts and Work/Chat output folders; listing them neither creates Atlas rows nor copies their bytes. The existing run-owned path remains the source until the user chooses **Save to Atlas**.

Page chats use the shared `WorkspaceInput`, attachment picker and conversation-settings hooks. Clicking the prompt expands the overlay while retaining the same compact toolbar as Browser and Review, without a Plugins button; permissions follow the same mode gates as other composers. Explicit context and transient upload bytes are owned by backend/account/Page/Work space, so switching Pages preserves unsent attachments without importing another chat's context. Accepted messages send a settings snapshot plus serialized uploads/context; failed sends retain the draft. The active Space supplies the Page chat's provider; remembered Space ids identify existing runs rather than override the active Space. Only a Work run belonging to that Space and provider can be continued. The overlay's options menu offers New page chat once a conversation exists. The editor flushes pending saves before sending; the user's message remains unchanged. Page identity travels separately as `atlasPageId`, is validated against the account and Work mode, and is retained in the run's config snapshot. The runs service composes the Page's current title/version and editing instructions into the provider's native instruction layer alongside mode, Space and project instructions on start, continuation and fork. Claude Page chats render fresh system instructions on resume; ordinary chats keep their system-prompt snapshot.

**New image** opens `/atlas/images/new`; accepted submissions open `/atlas/images/runs/:runId` with the ordinary Work transcript, approvals and continuation. This surface always uses a real account-owned Codex Space projected to Work, reusing an existing one or creating one if necessary, without switching the global Space. It discovers Image Gen through the canonical Codex skills list and preserves the skill’s actual file path, scope and mention metadata in composer context. Sending requires an available, user-invokable skill; missing or disabled skills show skill-specific guidance with a refresh action. Blank glass template cards replace the prompt and reselect that mention. The shared composer provides a direct image-only plus picker, paste/drop and transient previews, with native voice disabled on this surface. Text, context and uploads use the common composer ownership seams, scoped by backend/account/Space/project/run; rejected sends preserve the draft. Generated files retain normal run ownership and appear in Atlas through the existing generated-file projection.

Image discovery admits the native Codex `~/.codex/generated_images/<sessionId>` folder of each account-owned Codex run, with bounded flat discovery per thread. It never scans unrelated Codex threads. Images discovered through paths in conversation/tool events are excluded from Atlas even when recorded as run artifacts, so a run-folder copy of a native generation does not appear as another creation. Explicit `codex_image_generation` results remain eligible, including inline pixels saved under Mains user data when Codex returns no native path. Scanning `runs/<runId>/work` or `runs/<runId>/chat` supplies documents only. Run attachments enter the same read-only library projection through the runs service's verified-original seam. Their `origin: attachment` keeps them visible in All and out of Generated/Your creations. The Uploads view (`view=uploads`) in All, Docs and Images shows only these attachments, retaining project/search filters and the matching saved-copy actions; saving one to Atlas explicitly copies its original. Missing originals are skipped without hiding other items.

Recent Page rows and the editor share `AtlasPageMenu` for copying content, importing, exporting Markdown/JSON, history, project moves and Trash. Sidebar requests are scoped by backend/account and handled by the Atlas route, which waits for the current editor's save queue before opening another Page. Actions use that Page's live editor, including any recovered or unsaved draft; a request for an unopened Page is consumed once after its editor loads. Opening the options menu itself never opens the Page.

Successful Trash and permanent-delete mutations close the Page's tab under the backend/account that started the operation. The tab list also reconciles against the complete Atlas inventory to remove stale deleted Pages, retaining unknown tabs during loading or failed refreshes. Removing the active tab selects a remaining Page or returns to Pages when none remain. Opening a trashed Page remains read-only and does not recreate its tab; closing a tab preserves its working-chat draft.

The sidebar's **Trash** button opens `AtlasTrashMenu`, a search-only dropdown over the current account's trashed Pages, documents and images. Trash is not a library route scope. Rows open Pages through the route's save-aware request, documents in the viewer and images in the shared Atlas preview; they never restore on open. Restore updates the item in place, while permanent deletion uses the existing guarded backend operation after confirmation and closes the removed Page's tab. Search stays local to the dropdown and does not change the current route or library filters.

Page grid cards use `glass-card`, with the title/icon and options above an inert content thumbnail. The library requests previews only for grids containing Pages. One indexed list query reads at most 2,400 Markdown characters from each Page's current revision; list/sidebar queries omit that projection. Rendering is bounded to 18 plain-text rows with headings and list/task markers, without BlockNote, a Markdown renderer or HTML execution. At most one embedded Atlas image per card uses the existing signed-image cache and lazy image loading; additional or external images stay as captions. These excerpts are display-only; editing and history still use canonical blocks and full revisions.

All's grid uses responsive CSS columns in source order, flowing down each column before continuing to the next. Cards stay intact across column breaks. Page previews fit their bounded content and images retain their native aspect ratio on this surface; category grids retain their existing layouts. No JavaScript measurement or additional preview loading is needed.

`atlas_items` owns native Pages and explicitly saved files. Save to Atlas copies a single immutable snapshot to `<userData>/atlas/files/<itemId>/<safeFileName>`. A stable account + run + canonical-path source key makes repeated saves idempotent, while the source run/collection foreign keys detach on deletion. Conversation deletion removes its original outputs but leaves Atlas's copy. Documents and images have no revisions; generated files have no Atlas Trash state. Saved items have favorites, recoverable Trash and explicit permanent deletion.

Page presentation lives in nullable JSON `atlas_items.metadata` (`icon` in the existing emoji/icon registry format and `coverFileId` pointing at a permanent Atlas image). Metadata updates merge independently of content versioning; revision restore leaves the current icon and cover intact. A cover can reuse an existing saved image without copying it; current references, including trashed Pages, prevent permanent deletion of that file. Cover framing (`coverPositionY`) is device-local Redux persist state scoped by backend/account/Page and cover identity; it is absent from the database and revisions. Only that framing survives renderer restart in `atlasSlice`; tabs and chats remain session state.

Only Pages use `atlas_page_revisions`: canonical BlockNote JSON plus a Markdown projection, title, version and user/agent provenance. Saving compares the expected current version in the same transaction as the new revision; restoring an older revision creates another revision. The editor serializes autosaves and retains interrupted local drafts rather than overwriting concurrent agent/user changes. Local Page embeds are explicit permanent uploads referenced by `atlas-file://<itemId>`; `atlas_page_file_refs` protects files used by any restorable revision. The file explorer may read/save a copy of an exact registered Atlas file, while Atlas storage stays outside write roots. Work-mode Claude/Codex agents can create/update Pages through Atlas tools; Chat can only read them, and handlers derive ownership/mode from the actual run. Hosting/Sites are a later feature.

Page content and rendered Markdown share the document presentation utilities in `components/document-content.css`. `atlas-editor.css` applies them to BlockNote's native editable nodes, retaining its schema, authored colors, selection, checkboxes, table resizing and upload behavior. Editor menus, toolbars and file panels use the app's glass surfaces and neutral selection colors, scoped to the themed BlockNote roots so portalled controls inherit the same design. Assistant Markdown tables keep their lighter row-separator variant.
_Avoid_: importing every generated file into Atlas tables; automatically duplicating run outputs; using a Markdown projection as the Page's canonical format; revising documents/images; broadening file-explorer write roots to Atlas storage.

### search

The `search` module is a read-only, cross-aggregate projection for the global command menu. It owns no canonical table: `search:query` runs bounded, account-scoped reads over workspace metadata, run title/goal metadata, generated `document` artifacts, and the `run_artifacts_fts` search projection, then returns the small `GlobalSearchResult` navigation contract from `@mains/contracts/search`. The FTS5 projection contains only visible conversation text (`user-prompt`, `report`, and `result`), is backfilled by its migration, and stays synchronized through `run_artifacts` insert/update/delete triggers; tool logs, files, and internal thinking never enter it. Its `unicode61` tokenizer and 2/3-character prefix indexes make partial multilingual queries fast without treating user input as FTS operators. Run/document hits carry provider, mode, space, workspace, and collection ids so the renderer can restore the run's experience before opening it. Local commands and Pulse/prompt suggestions never enter SQLite; `cmdk` supplies keyboard/list semantics and `fuzzysort` ranks that in-memory catalog.
_Avoid_: routing global search through the canonical-content `entities:search` endpoint; returning whole workspace/run/artifact rows; scanning transcripts with `%LIKE%` on each keystroke; indexing tool output or thinking as chat content; putting command execution in the search service.

### backend

The `backend` module is **this install as a backend**: its identity and who may talk to it. It owns the `app_settings.backend_id` column (a stable id minted on first use, never rotated — a paired phone keys its saved backend on it) and the `paired_devices` table. Two credentials with deliberately different lifetimes: a **pairing code** (minted by the desktop, shown as a QR, five minutes, single exchange, memory-only) and a **device token** (what the code is exchanged for; long-lived, stored on the phone, stored here only as a `token_hash`, revocable per device). `backend:describe` is the one IPC channel — registered through the shim so it is reachable over WebSocket, and the first thing a remote client asks. Pairing itself has no channel: `POST /pair` and the handshake-time `verifyDeviceToken` reach the service through hooks the WS host is given.

**Paired-device allowlist**: a device token authenticates *less* than the shared pairing token. `verifyDeviceToken` returns the device plus `PAIRED_DEVICE_CHANNELS` — the read-only channels a phone may invoke — and the WS router (`ws-server.ts`) refuses anything else before a handler runs, so no module needs to know about devices to be safe from one. `describe` shows a paired device only the namespaces it can reach.

**Command receipts**: the mutations a device may issue (`PAIRED_DEVICE_COMMANDS` — answer a request, continue a run, start one, switch a space's mode, edit a provider's run settings — effort, permission mode, fast / goal / plan — via the patch-shaped `providers:updateRunSettings`, while `providers:update` stays desktop-only) are reachable only with a `commandId` on the invoke frame. The WS router keys `command_receipts` (owned by `backend`) on device + commandId: a finished command replays its stored, wire-encoded ServiceResponse; one still running makes the retry wait for the same result (module-level in-flight map, because the retry arrives over a *new* socket). Idempotency is therefore a transport concern like the allowlist — no `runs.*` handler knows about it, and the desktop never sends a commandId. Receipts expire after seven days. Terminal, filesystem, git and settings never become commands. Outbound pushes are filtered the same way: `PAIRED_DEVICE_EVENTS` lists what the WebSocket sink may forward to a device connection — everything else on the bus stays between the desktop's own processes. And responses can be projected per caller: `providers:getEnabled` answers a paired device through `providerForPairedDevice`, its `config` reduced to `RUN_SETTING_CONFIG_KEYS` so credentials never leave the Mac.

Three neighbouring modules are easy to confuse, so the split is by *direction*:
- **backend** — me as a backend (identity, paired devices). Served by both the desktop app and headless `serve`.
- **localBackend** — exposing this machine (WS host lifecycle, bind/port, Tailscale serve, addresses). Desktop-only, real `ipcMain` (local-only control: a remote client must never toggle the exposure it rides on). Owns the desktop-facing pairing handlers (`localBackend:createPairingCode/listPairedDevices/revokePairedDevice` + the `pairedDevicesChanged` push) because a code needs the host's reachable addresses.
- **remoteBackends** — *other* backends this desktop connects to: the encrypted at-rest store for their pairing tokens (`remoteBackends:setToken/getToken/deleteToken`; the catalog of `KnownBackend`s lives in the renderer). Formerly `backendAuth`.


**backend runtime**:
The small host-capability seam in `packages/backend/src/runtime/backend-runtime.ts`. Backend
modules ask it for data paths, app metadata, credential encryption, URL opening,
sleep inhibition and optional image previewing; they never import Electron for
those capabilities. The desktop composition root installs the Electron adapter,
while the standalone composition root installs the Node adapter. Native folder
and Save As dialogs and OS run notifications are client adapters, not backend
handlers, and are registered only by the desktop root.
_Avoid_: importing `electron` from a module reachable through `serve.ts`; adding
an Electron-shaped fake to the Node entry; exporting an Electron adapter through
a barrel used by backend modules.

**standalone server**:
The plain-Node backend composed by `apps/server/src/standalone-server.ts` and
`apps/server/src/server-cli.ts`. The application owns one SQLite database,
handler registry, schedulers, provider processes, terminals and WebSocket host
for its lifetime, then drains them in reverse order on shutdown. Its default
`userData` is Electron's existing canonical Mains directory, so both hosts see
one database and managed-file history without an import. They use it serially:
the shared **database ownership** seam claims a process lock before SQLite opens
and rejects Desktop/Server overlap because each host also runs schedulers,
provider processes and automations. Existing Electron-encrypted integration
credentials stay preserved; the Node host cannot decrypt those records and
stores its local-key AES-GCM (`MNS1`) credential alongside them after
reauthorization. Each host rotates and selects its own encryption format, so
reauthorizing in Server no longer invalidates Desktop (or vice versa). The Electron-free
implementation lives in `packages/backend` and
is consumed by both hosts through `@mains/backend`; server-only entry, CLI,
build and packaging code live in `apps/server`, while native UI adapters live in
`apps/desktop`. One backend process owns the canonical data directory at a time.
_Avoid_: treating standalone as an Electron `--serve` alias; pointing it at the
desktop data directory without ownership enforcement; deleting or disabling
Electron-encrypted credentials merely because Node cannot read them; returning
to one global-current credential slot across incompatible encryption formats; starting
another server against the same state directory; adding server-only composition

## Operations

### Workspace intake

The main-process operation that turns a git repo into a **project** + **workspace** pair. It has two seams. *Acquisition* — how a local repo path is obtained: `folder` (an existing path the user picked), `clone` (cloned from a URL via `gitService.cloneRepo`), `init` (a fresh empty repo via `gitService.initRepo`), or `worktree` (an additional worktree workspace for an *existing* project, fed by `project.rootPath` — the project already exists, so the find-or-create step is a lookup). *Intake* — the uniform tail run on that path: worktree-or-direct git import (`importLocalRepo` / `importLocalRepoDirect`) → `findOrCreateProject` → derive the project's `workspacesPath` → assemble the workspace `metadata` → `createWorkspace`. The **intake** is the deep, shared core; the four acquisitions are thin front-ends that feed it a path. All four enter through the single `workspace:createFromSource` channel as source kinds.

Every Workspace belongs to exactly one Developer Project (`workspaces.project_id NOT NULL`, `ON DELETE RESTRICT`). Legacy orphan rows are backfilled into local Projects by the migration. Project removal therefore goes through the deep lifecycle that deletes its runs/reviews and Workspaces before deleting the Project row; raw FK cascade or nulling is deliberately unavailable because it would bypass provider-session and worktree cleanup.

Owned by `workspace.service`, which calls `gitService` and `projectsService` (same cross-service shape as `projects.service.listIssues` reaching the `entities` barrel). The worktree-vs-direct ordering difference lives entirely behind the intake seam: the worktree path lands under `worktrees/{projectName}/`, so it must `findOrCreateProject` *before* the import; the direct path imports first and reads `originUrl`/`baseBranch` off the result. `init` stays direct-only (a brand-new repo lives at its real path); `folder` and `clone` honor `appSettings.enableWorktrees`. The renderer keeps only the picker invocation, navigation, toast, and modal state.
_Avoid_: re-inlining the find-or-create-project / `metadata` / `createWorkspace` tail at call sites (it was duplicated 5× across `use-sidebar-actions.ts`, and survived a 6th time in `workspace-list.tsx`'s create-worktree flow before the `worktree` acquisition absorbed it), orchestrating the git → projects → workspace sequence from the renderer, or string-deriving `workspacesPath` outside the intake.

### Workspace git operations

Renderer-triggered git effects that also touch workspace state are **workspace operations**, not git channels: `workspace:renameBranch` resolves the branch actually checked out at `workspace.rootPath` and renames it against the worktree's source repo when applicable; `workspace:switchBranch` checks out an existing branch in the workspace's own path (never a worktree's source repo — git refuses on its own if the branch is checked out elsewhere), announces the branch it actually landed on, and re-records the diff, which was anchored to the old branch's HEAD; `workspace:createBranch` forks a *new* branch off the current HEAD and checks it out — the counterpart to `switchBranch` for a name that doesn't exist yet, and the one branch operation that needs no diff resync, since `checkout -b` leaves HEAD on the same commit (uncommitted work comes along by definition, so there is nothing for git to refuse and nothing to warn about). It is also the only branch operation that writes `workspaces.baseBranch`, repointing it at the branch forked off — read before the checkout moves HEAD, and best-effort, since a branch git already created must not be undone by a failed row update; `workspace:discardPaths` takes an explicit file list, restores each to its **HEAD** state (deleting the ones HEAD never had) and re-records the diff. It is anchored to HEAD rather than to a recorded diff's `baseRef` because it undoes what a caller is *showing*, which exists even when no run ever recorded a diff row — the older whole-tree `workspace:discardChanges` (reset to `baseRef`) was removed with the diff summary bar, its only caller. The current branch is never persisted. `workspace:listGitStates` reads it live from git for every workspace, and the main process watches each workspace git directory's `HEAD`, emitting `workspace:gitStateChanged` when an external checkout or rename changes it. These operations were previously orchestrated inside components via `api.git.*` calls, with the renderer holding git semantics like the worktree `sourcePath`-vs-`rootPath` distinction.
_Avoid_: orchestrating multi-step git + workspace-state sequences in the renderer; deciding worktree source-vs-root paths outside `workspace.service`.

**Branch model**:
`projects.defaultBranch` is the repository integration branch. `workspaces.baseBranch` is that workspace's explicit PR target. The workspace's current/head branch exists only in git and is read at display/action time; there is deliberately no workspace `defaultBranch`, `currentBranch`, or `metadata.worktree.branch` field. Direct intake keeps the checked-out branch live while resolving the base from `origin/HEAD` (then conventional local `main`/`master`, then current checkout). Worktree intake creates the new branch explicitly from the project default branch. `baseBranch` moves exactly once after intake: branching off `dev` repoints it at `dev`, because work started there proposes back there. That is a record of where a branch *came from*, not of where HEAD is — the PR form's base picker still overrides it per pull request without writing anything back.
_Avoid_: persisting the checked-out branch; deriving PR base from the current checkout; using cached workspace metadata for commit, push, PR head, or rename.

## git module

The `git` module is **main-process-internal**: no IPC channels, no preload namespace, no renderer caller. The renderer reaches git effects only through operations owned by domain modules (**workspace intake**, **workspace git operations**, `gitFlow`, and `projects:listBranches` — the settings branch dropdown reads branch names via `projectsService.listBranchNames`, which owns the `remotes/…`-prefix dedup). The former `git:*` namespace (18 channels, only 4 ever called from the renderer) was deleted; the live flows moved behind workspace/projects seams.
_Avoid_: re-adding `git:*` IPC channels or a preload `api.git` namespace.

**throw-style**:
`gitService` methods return plain `T` and throw on failure — no **ServiceResponse** inside the service. The envelope is constructed only at the IPC seam by the shared `handle()` wrapper in `packages/backend/src/ipc-kit/` (catches, logs, normalizes the message, returns `fail(...)`; wraps the return in `ok(...)`). Internal callers (`gitFlow`, `workspace`, `runs`, `projects`) consume plain values — no `.success` unwrapping.
_Avoid_: returning ServiceResponse from `gitService` methods; hand-rolled unwrap helpers over git results (`expectOk`, `readOriginUrl`-style wrappers).

**DiffSnapshot / captureDiffSnapshot**:
The deep diff-capture operation, `gitService.captureDiffSnapshot(rootPath, baseRef)` → `{ baseRef, diffText, files, untrackedFiles, shortstat }`: unified diff since `baseRef` including synthetic hunks for untracked files (small text inlined, large/binary stubbed) and an untracked-aware shortstat. **All-or-throw**: a partial git failure throws instead of silently degrading fields to `""`/`[]`, so an empty `diffText` always means "clean tree" (callers like run-session map a thrown snapshot to "baseline unknown"). The four diff primitives it composes (diff-since, changed-files-since, shortstat-since, untracked-files) are an **internal seam** — used by the module and its tests, not exported from the barrel. Formerly `workspace/workspace-diff-snapshot.ts` (`buildDiffSnapshot`), which lived in the wrong module, was imported by `runs` and `gitFlow` from the file path rather than a barrel, and had a degraded hand-rolled copy in `gitFlow.performCommit` (no synthetic hunks, empty shortstat).
_Avoid_: exporting the diff primitives from the git barrel; hand-composing diff + untracked + shortstat outside `captureDiffSnapshot`; treating a snapshot failure as an empty diff.

**git test surface**:
Semantics-bearing methods (`captureDiffSnapshot`, `importLocalRepo`/`importLocalRepoDirect`, `initRepo`, `push` auto-upstream, `getBranchDiff` three-dot, `discardPaths`, `checkoutBranch`, `renameBranch`) are tested against **real temporary git repos** (tmpdir fixture helper), not a mocked simple-git — the old mock-forwarding tests verified argument passing, not git behavior. Pure pass-through methods need no tests.
_Avoid_: re-introducing wholesale `vi.mock("simple-git")` tests for semantic methods.

## Provider adapters

Vocabulary for the `providers/adapters/` subsystem, where one unified `WorkRunAdapter` interface fronts four agent SDKs (Claude, Copilot, Codex, Cursor).

**Claude runtime**:
The executable selected by `resolveClaudeRuntime` in `providers.utils.ts`: a valid explicit `config.binary` override, otherwise the Agent SDK's version-matched native dependency. Packaged Electron resolves the executable outside ASAR; development and the standalone Node host resolve it beside the SDK. Runs, model/command discovery, account/version probes, plugin commands, login and onboarding availability all use this selection. Login receives a shell-quoted command through CLI metadata. The bundled runtime updates with Mains, while an explicit external executable retains its own update action. Control queries use the run's authentication environment and release their processes after reading metadata; the version-free model list is only a discovery-failure fallback.
_Avoid_: auto-selecting the system `claude` for discovery while runs use the SDK bundle; treating the absence of a system install as unavailable or signed out; self-updating the SDK-matched bundled executable.

**Copilot runtime**:
The executable selected by `resolveCopilotRuntime`: a valid explicit `config.binary` override, otherwise `copilot-runtime` from the host SDK's `@github/copilot-sdk-<platform>` package. Its adjacent `runtime.node` and supporting assets ship outside ASAR in packaged Electron. Runs, model/command discovery, account/version probes and onboarding use this selection. Account checks use a short-lived SDK control client, release it without creating a model session, and read newly saved login credentials without interrupting an active run. The headless runtime has no login command: shell-quoted CLI metadata selects the matching full `@github/copilot-<platform>` CLI for device login, sharing Copilot's saved credentials. An explicit override supplies both execution and login. Bundled executables receive `--no-auto-update` and update with Mains; an explicit external CLI retains its own update action. GitHub CLI authentication remains a runtime fallback, not a Mains prerequisite.

Copilot Fast Mode is the SDK's integrator-only `capi.autoTier: "fast"` latency preset for the `auto` model; fixed models do not advertise the toggle. Conversation snapshots override the provider default, including explicit `false`. Create and resume forward the preset, while turning it off on resume calls `setAutoTier(null)` because omission would preserve the native session's saved preference. Preference changes can remain pending until the next successful Auto turn; native activation failures appear as warnings and retain the previous setting.

Copilot streaming is enabled on create and resume. Each main-agent message/reasoning block accumulates SDK `deltaContent` into an ephemeral snapshot keyed by its native id; subagent deltas stay out of the main transcript. Only complete messages are persisted, retaining `metadata.streamId` so the renderer replaces the live preview by identity even when final text changes. Reasoning previews use the thinking lane and clear on completion; unfinished buffers clear when the turn ends or fails.

The Copilot driver imports its client, session, tool, hook and permission contracts from the installed SDK. Run permission grants use `approve-once`; a `managedApprovalRequired` request always goes through the user approval broker, including in bypass mode, and a user's approval is marked `approvedInteractively`. Native hook timestamps are Dates and their workspace field is `workingDirectory`; the driver translates these at the shared package-guard boundary. Background discovery/generation sessions defer managed approvals because they have no user approval surface.

`copilot-approval.ts` projects native permission requests into canonical approval actions (`Edit`, `Write`, `Delete`, `Bash`, `Read`, `WebFetch`, or the actual MCP/custom tool), with only decision-relevant input. Native intentions, sandbox access scope and warnings remain visible as descriptions; protocol ids and policy flags do not become parameter rows. File writes retain their patch for the shared diff preview, and shell requests use `fullCommandText` rather than parsed command fragments. The approval dialog scrolls its content independently of its action buttons; skills have a compact name/arguments preview.

For runtimes started by Mains, provider `githubToken` maps to SDK `gitHubToken` and explicit `useLoggedInUser` values are preserved; omitted values keep SDK defaults. These credentials come from provider configuration, never conversation snapshots. Authentication changes invalidate discovery caches and replace the run client after active turns finish; short-lived account probes read the new configuration immediately. An external `cliUrl` server manages its own authentication, so its `forUri` connection receives neither local authentication option.
_Avoid_: requiring a global Copilot or `gh` installation; running model or account probes through the login CLI; invoking `login` on the headless runtime; shipping its native library or support assets inside ASAR; storing a resolved bundled path as an explicit binary override; letting a bundled executable select a cached update.

**Cursor ACP runtime**:
The local `agent acp` process speaks ACP v1. One initialized process serves sessions, while active prompts route notifications and server requests by `sessionId`; an extension without session identity is accepted only when one prompt owns it. Each run owns its own Mains MCP bridge, passed through `session/new` or `session/load`, without writing project or user `.cursor/mcp.json` files. Acquisition failures release that bridge. Prompt notification, request and bridge events share an ordered projection queue which drains before the terminal outcome; completed prompts no longer receive late notifications.

`cursor-message-stream.ts` owns assistant text projection: it holds and removes Cursor's title-only YAML frontmatter across streamed deltas and recognizes dedicated transport diagnostics such as `WritableIterable is closed`. A diagnostic-only ending fails the turn even if Cursor returns `end_turn`, preserving the preceding reply and clearing live previews. The exact `Error: RetriableError: WritableIterable is closed` diagnostic is treated as a stream-close artifact only when the prompt RPC returns `end_turn`, final reply text is present, no tools remain pending and the prompt was not canceled; it stays in internal logs without failing the completed turn. Other transport diagnostics, empty replies and RPC failures still fail. Error explanations, quoted diagnostics and fenced code remain conversation content. Native `session_info_update` titles update run metadata without becoming transcript messages; a trailing `<|eos|>` token is removed from this title. ACP `plan.entries` snapshots feed shared execution progress; plan proposals remain separate. Only Mains MCP calls are suppressed as bridge duplicates; external MCP calls keep their native tool rows.

Tool presentation titles stay in metadata, never injected as `_title` parameters. Native file `path` fields map to the shared `file_path`, while generic titles such as `Read File` and `Run Shell Command` do not invent arguments. ACP content wrappers and legacy bare text blocks both project tool output. A structured error result or nonzero shell exit fails that tool even when Cursor sends `status: "completed"`; the agent may recover and finish the turn successfully. Missing native MCP identity remains a generic MCP row.
_Avoid_: forwarding session titles as `sdk-user` messages; treating Cursor's synthetic transport error as successful assistant output; replacing another run's bridge or prompt handler; suppressing every MCP tool; rendering execution-plan entries as plan proposals.

**Codex app-server client**:
The deep process/transport module in `codex-app-server.client.ts`. It owns one `codex app-server` child process, JSON-object framing over stdio, typed request/response correlation and timeouts, notification/server-request routing, and deterministic pending-request cleanup on exit or shutdown. `codex.driver.ts` owns process initialization, the **Codex session acquisition module** owns thread/turn acquisition, and the **Codex run coordinator** owns live request routing and run completion. All reach the transport only through the client's small interface. The client itself does not know about runs or workspaces.
_Avoid_: spawning `codex app-server`, parsing its stdout, tracking JSON-RPC request IDs, or managing pending RPC timers inside `codex.driver.ts`; moving run/thread semantics into the transport client.

**Codex run coordinator**:
The per-driver lifecycle module in `codex-run-coordinator.ts`, created through `createCodexRunCoordinator(...)`. It exclusively owns live run state, in-memory run→thread and turn→run identity, thread/subagent routing, serialized notification queues, server-request ownership, exactly-once turn finalization, usage flushing, and abort/timeout/cleanup/shutdown semantics. Turn ownership is captured synchronously from `turn/started` because current turn-scoped notifications such as `turn/plan/updated` carry `turnId` without `threadId`; this keeps concurrent runs isolated before their async mapper queues execute. Its interface lets the **Codex session acquisition module** register or attach threads, while `codex.driver.ts` executes prepared `CodexRunSession` values, cleans up runs, and installs routing on a live **Codex app-server client**. Timeout and active abort both send `turn/interrupt` before finalizing; an already-aborted signal never starts a turn. Every coordinator instance owns independent maps so an invalidated/old provider adapter can finish without mutating its replacement.
_Avoid_: module-global Codex run/session maps; routing notifications or server requests inside `codex.driver.ts`; routing a turn-only notification through the single-active-run fallback; resolving a run before its interrupt request has been dispatched; treating a subagent `turn/completed` as parent completion.

**Codex session acquisition module**:
The deep acquisition module in `codex-session-acquisition.ts`, created through `createCodexSessionAcquisition(...)`. It implements create, resume, fork, and review acquisition plus existing-thread voice preparation; it owns effective thread/turn settings, context/issue/signal/file/skill/attachment input construction, archived/missing-thread behavior, goal-establishment calls, coordinator registration, and prepared `CodexRunSession` construction. `codex.driver.ts` injects app-server access and persistence seams, then delegates the four `ProviderDriver` acquisition verbs directly. Voice preparation resumes an idle thread with its execution settings and neither submits a prompt nor mutates its tracked goal. Attaching the voice coordination bridge requires the existing work turn to finish first; it never reconfigures a live turn.
_Avoid_: reconstructing `thread/start|resume|fork`, `turn/start`, or `review/start` parameters in `codex.driver.ts`; maintaining separate create/continue prompt builders; dropping typed context while adapting fork or continue requests; moving execution, notification routing, or finalization out of the **Codex run coordinator**.

**Codex capability module**:
The deep discovery/management module in `codex-capabilities.ts`, created through `createCodexCapabilities(...)`. It owns Codex model, account, rate-limit, skill, and plugin operations; maps their app-server responses into shared adapter types; and hides plugin feature gating, TTL/in-flight cache deduplication, marketplace reference indexing, mutation invalidation, and connector-directory enrichment behind a small object interface. `codex.driver.ts` supplies the live app-server and CLI-health dependencies, delegates `ProviderDriver` capability methods to this module, and retains app-server and goal lifecycle orchestration.
_Avoid_: reintroducing capability response mapping, plugin catalog caches, feature-gate state, or remote plugin identity resolution inside `codex.driver.ts`; moving run/thread notification semantics into the capability module.

**native voice session**:
A conversation-scoped Codex realtime call, independent of a work turn's lifetime. New-chat microphone activation first creates an idle run through `runs:createRealtimeConversation`, preserving draft text, uploads, settings and pane ownership. Native preparation creates and persists an empty thread when needed, without a synthetic prompt, text turn or goal request; existing threads are resumed. The first final user transcript supplies the initially empty goal. Conversation readiness is probed again as voice connects or ends, so text can continue the same thread afterward. `codex-realtime.ts` owns native v3 WebRTC signaling, transcript identity, and connection-scoped teardown using app-server authentication; it lets app-server manage work handoffs. The **Codex run coordinator** retains thread ownership between delegations, installs a work sink synchronously at the parent's `turn/started`, and serializes fresh `RunSession` creation/completion so approvals, tool events, Git boundaries and usage keep their normal path. Ending voice alone closes the call; the owning composer Stop closes voice and stops its current work turn independently. The renderer's one app-scoped `realtime-voice-controller.ts` owns microphone tracks, peer/data channel, audio playback and the original backend transport. Composers only subscribe. Connection readiness requires both native start and connected media; stop/failure releases the microphone immediately. A failed stop retains native ownership and the service claim until confirmation or process exit, while the renderer shows that the microphone is off and offers an id-scoped close retry. Pending closure blocks another call or text response. Navigation between chats, editors, spaces on the same backend and routes preserves the call. Only the actual visible main transcript registers its run with the local `voice-chat-presence.ts` store; a composer target does not imply that chat is visible. Its own chat shows only the reactive orb above the input. `composer-controls.ts` projects one primary action in both new and existing chats: an owned call keeps Stop priority. Running work shows Send for text, attachments or explicit context when the composer supports queuing/steering, including queue edits; an empty running draft or a composer without that capability shows Stop. The send action reuses the existing queue delivery mode (queue by default, steer when explicitly selected) and returns to Stop after the submitted draft clears. An empty idle draft starts voice with the microphone icon; other idle drafts use Send. There is no separate voice-start button. The same Stop closes voice and stops the composer's current work independently; native closure does not delay stopping work, and a pending voice close leaves run Stop enabled. The call's own composer adds icon-only mute/unmute immediately before Stop, including cancellation during connection preparation and retry during unconfirmed closure. Other chats keep their normal text actions; another call cannot start while voice is owned. Lifecycle-level error notifications replace text around the orb. Other views show the compact dock in the navigation rail immediately above spaces, separated by a divider. Its 32px reactive orb opens a menu with mute/end/retry controls and navigation to the original run; narrow layouts without a rail retain a compact floating fallback. Returning uses the run's original space, provider, mode and workspace rather than current selection. Host replacement, transport disconnection, app unload and app-shell disposal still end the call. User/assistant speech streams in the chat through existing ephemeral snapshots, without a second transcript in the voice bar. Final speech persists into existing artifacts with the same stream identity and speech-start timestamp, retaining its bubble and position. Voice previews survive work completion and remain until the persisted identity arrives; closing drops only unfinished speech for that connection. Final user and assistant speech remains visible after the call ends, including voice-only conversations without written replies. The pure `voice-transcript-view.ts` annotates work from frozen input provenance. A native delegation records `inputSource: voice`, its call/native turn ids and terminal outcome in existing turn metadata; its messages, tools and logs carry the same ids from their first event. `projectVoiceTranscriptEvents(events, turns)` hides only non-voice assistant reports belonging to that native voice work, including live written previews before turn metadata loads. Spoken user/assistant messages, ordinary tools, logs, plans, MCP Apps and generated deliverables stay in the chronological chat timeline. There is no separate work disclosure or empty delegation card. This provenance-based choice survives closure and reload, preventing duplicate written narration from reappearing. Text-originated turns keep their normal assistant messages independent of call state. Legacy call/turn evidence can recover older work without text matching; ambiguous ownership stays in the regular layout. Raw artifacts are unchanged, and speech retains the turn where its first transcript arrived. Partials and call ownership stay in memory. Transcript invalidation remains subscribed for the selected idle tab, and a fresh running status re-arms the run cache's terminal handling.
Voice work orchestration uses a session-scoped `mains_voice` stdio MCP bridge, advertised through per-thread Codex config on start/resume. Ordinary SDK tool catalogs exclude this voice scope. Only the generated session-local bridge uses `default_tools_approval_mode: approve`; worker permissions and other MCP server policies keep their own settings. The backing agent receives coordinator instructions: delegate project/multi-step work into a separate visible run, retain short conversation/lookups here, reuse a stable task key, and forward explicit user corrections to the same worker. The runs-module deep helper `voice-task-coordinator.ts` injects existing run service operations into those tools, restricts reads/mutations to linked chats owned by the same account, serializes follow-ups and checks stable delivery ids before retrying. The worker inherits the parent's space, workspace, mode, model and permission snapshot; it does not receive the voice tool bridge. Existing report-artifact metadata stores the navigation link and existing context metadata attributes the worker's user prompts. The renderer preserves these as flat `voice-task-card.tsx` navigation rows; successful management tool calls do not add another transcript block. Workspace tab lists admit scoped backend `runs:updated` notifications without changing selection; initial list loads and stale lookup responses cannot discard or overwrite the newly created worker.
The coordinator follows worker status/persistence/approval notifications while the call is active. Coalesced updates go through the existing voice event channel and the controller's WebRTC data channel using Codex 0.160's v3 `session.context.append` wire format: `input_text` content entries, no channel for quiet progress, and `channel: commentary` for verified terminal/attention updates. The controller also owns `realtime-voice-audio.ts`: analysis-only Web Audio branches of the same local/remote streams, disposed alongside media. `VoiceOrb` samples their noise-gated, smoothed levels without updating React/Redux per frame; its fixed circle contains flowing gradients. Hidden/offscreen drawing pauses, reduced motion uses a static gradient, and visualization failures do not fail the call.
_Avoid_: a second microphone per composer; sending PCM through the ordinary IPC/event bus; a new voice database table or migration; auto-starting voice or work on mount; manufacturing `turn/start` for a native delegation; unsubscribing an open call at each work completion; letting a late stop/event target a different connection; requiring a separately configured API key for the native ChatGPT-login path; storing animation samples in React/Redux or routing analysis back to speakers. Avoid text-similarity deduplication between voice narration and written work, hiding finalized speech after closure, or classifying turn origin from the current microphone state.

The **Codex run coordinator** resolves each request to its live run and supplies run state/tool context.
Field-bearing MCP form requests reach the existing input broker as `kind: "elicitation"`, with the schema carried by the shared request DTO. `shared/mcp-elicitation.ts` owns the flat field model and validation used on both sides of the transport: text, numbers, booleans, titled single/multiple selections, defaults and constraints. Each request owns fresh local form state; values return as typed JSON through the existing `answer` string. Explicit cancellation, timeout, provider closure and run abort cancel the form; a decline remains a distinct response. Session approvals cover empty confirmations only and never answer a subsequent form on the user's behalf.
_Avoid_: switching on server-request methods or constructing their response shapes inside `codex.driver.ts` or the **Codex run coordinator**; opening approval UI for a dead run; moving notification-to-event projection into the request broker; accepting unsupported form fields as an empty confirmation; caching or persisting user form answers.

**mains tool**:
An in-house tool exposed to coding agents across the drivers — `SaveReview`, `SaveFinding`, `SaveFindings`, `CheckPackage`. Git ceremony is deliberately absent: commits and PRs belong to the **git-actions panel** (or the agent's own shell), not to a mains tool. The handler logic lives once in `mains-tools.core.ts`; the parameter schema lives once in `mains-tools.schemas.ts` as a Zod object (the single source of truth — `z.infer` types the handler's args, `z.toJSONSchema` feeds the SDKs that want JSON Schema). The human descriptions are the existing `TOOL_DESCRIPTIONS` map.
_Avoid_: re-declaring a mains tool's parameter schema, required-fields list, or description inside a driver.

**tool registry**:
The deep module (`mains-tools.registry.ts`) that assembles each **mains tool** into one entry — `{ name, description, schema, handler, providers, modes }`. `name` is bare (`SaveReview`); namespacing/prefixing is a **tool renderer** concern. `providers` is an explicit allowlist of which drivers expose the tool; `modes` (absent = every mode) is the same allowlist along the experience axis. Developer tools remain developer-only; Claude and Codex expose `AtlasReadPage` in every mode and `AtlasCreatePage` / `AtlasUpdatePage` only in Work. Codex's request broker checks this same per-mode registry using the active run's mode, carried on start, resume, fork, and realtime registration. Dispatch is a registry lookup (`registry[name].handler(args, ctx)`), not a per-driver `switch`. The leaf `mains-tools.schemas.ts` has no dependencies, so the flow `schemas ← core ← registry ← driver` stays acyclic.
_Avoid_: a per-driver hand-maintained tool list, or a `switch` keyed by tool name (look up the registry instead).

**tool renderer**:
The per-SDK adapter at the **tool registry**'s seam. `toClaudeTools` yields Zod raw shapes for the in-process MCP server; `toCopilotTools` yields JSON Schema with the `mcp__mains__` name prefix and a `{content}`→string return; `toMcpToolDefs` yields JSON-Schema `inputSchema` defs embedded in the Cursor stdio script; `toCodexDynamicTools` yields Codex's dynamic-tools shape. Each renderer filters the registry by each tool's `providers` allowlist, so per-driver differences (naming, return shape, availability) live only here. Two formats already vary across this seam (Zod + JSON Schema), so it is a real seam, not a hypothetical one.
_Avoid_: hand-writing a tool definition inside a driver instead of rendering it from the registry.

`CheckPackage` is intentionally **absent** from Claude and Copilot: those drivers enforce package safety through a PreToolUse Bash hook that intercepts install commands, so they need no explicit tool. Codex and Cursor cannot hook that path, so they expose `CheckPackage` as a callable tool. This asymmetry is encoded in the tool's `providers` allowlist and is deliberate — not drift to be "fixed."

**mode harness**:
The per-run bundle a space's mode (`developer | work | chat`, `@mains/contracts/modes`) contributes to a run: a prompt delta, a **ModeToolPolicy** (`allowedTools` replacement + `disallowedTools`), and per-provider `configSnapshot` defaults/overrides — all declared once in the `MODE_HARNESSES` table (`src/shared/mode-harness.ts`). Resolution happens exactly once, in `runs.service`, from the run row's `mode` snapshot (`runs.mode`, stamped at start so resume/fork keep the original mode); the composed values ride the per-run request fields `extraInstructions`, `toolPolicy`, `configSnapshot`, and the row persists what actually ran. Drivers apply, never decide: claude appends the delta to its system-prompt preset and feeds the policy to its allow/disallow lists *and* its permission bridge; copilot layers the session `systemMessage` and denies via its PreToolUse hook; codex sends `developerInstructions` and a sandbox override (chat = `read-only`); cursor prefixes the prompt and switches agent mode (chat = `ask`). Precedence is `configOverrides > caller payload > configDefaults` — work's `acceptEdits` is a suggestion, chat's read-only lock is not. Codex's `planMode` (work + chat) and `goalMode` (chat) are overrides too: both flags live on the shared provider row and are toggled only from the developer composer, so a Code space that left them on has no legitimate claim on a Work/Chat run — and the codex driver applies the snapshot on create, resume, *and* fork (`runTogglesFor`), since a pin that held for one turn only is not a pin. A replacement `allowedTools` also withdraws the blanket trust both drivers grant `mcp__*` tools (claude's bridge `restrictedToolset`, copilot's `allowedOverride`): a mode that removed Write must not get it back through an MCP server the space happens to have attached. Mains-tool exposure per mode is the **tool registry**'s `modes` allowlist, not the policy's. Developer is locked to all-null/empty: the harness is behaviorally invisible until a space opts into work or chat. The UI half of a mode lives in the renderer's `MODE_CONFIGS` (`mode-config.ts`) as capability flags read through `useModeConfig`. Which modes a provider drives at all is a third table, `PROVIDER_MODES` (`@mains/contracts/modes`): copilot and cursor are developer-only for now, so the mode picker hides itself for them, `spaceService` refuses the pair on write and clamps it on read, and pulse validation rejects it. Their harness rows stay in the table, unused — re-enabling is one line.
_Avoid_: pre-approving a tool class (`mcp__…`) unconditionally in a permission gate; branching on `mode` inside a driver; writing mode state into the cached `AdapterConfig`/`adoptConfig` (adapters are shared across concurrent spaces — it races); re-declaring a mode's tool list or prompt delta outside `mode-harness.ts`; resolving the harness anywhere but `runs.service`; composing `configSnapshot` at a call site instead of `composeConfigSnapshot`.

## Renderer layering

**components/ui**:
Feature-agnostic primitives — buttons, inputs, modals, icons, spinners, toasts. They sit *below* every feature and may not import from `features/`: a primitive that reaches into a domain stops being reusable and drags that domain into everything that renders a button. Enforced by `no-restricted-imports` in `eslint.config.mjs`, alongside the existing rule that consumers import from the `@/components/ui` barrel (only `icons`, `icons/space`, and `icons/file-icons` are importable directly). When something generic is discovered inside a feature — as `FileIconComponent`, a pure filename→icon map, was inside the file explorer — it moves here rather than being imported across the boundary.
_Avoid_: importing `@/features/…` from anything under `components/ui/`; deep-importing a primitive past the barrel.

Compact icon actions use `Button variant="icon"`: one neutral light/dark hover surface, 12px radius, centered glyph and visible keyboard focus. Toolbar controls share the default 28px area and 16px glyph; `iconSize="sm"` (24px) and `"xs"` (20px) serve dense rows and embedded clears. Callers add positioning, visibility and semantic active/status colors; geometry, padding and hover fills stay in the primitive. Text actions, navigation tiles and image-overlay controls keep their own variants.

**components/layout**:
The app shell that hosts whatever route is active: `main/` (route table), `sidebar/`, `right-panel/`, `page-shell`, `resize-handle`. A shell exists to compose features, so importing from `features/` is the *correct* direction here and is deliberately not linted. What does not belong is feature UI that merely happens to be positioned by the shell — the session panel (environment, sources, deliverables) and the subagent panel both lived here and were only ever about the active workspace's run; they live under `features/workspace/components/` now, and the shell renders them from `App.tsx`.
Plugins and MCP App route shells render immediately after rail navigation. The Plugins page loads its feature content within its own Suspense boundary, keeping the page heading visible while the code and data load.
_Avoid_: adding a panel to `components/layout/` because that's where panels used to go — ask whether it renders anything outside its feature's state.

## MCP App extensions

**app entrypoint**:
A plugin tool that explicitly declares a `global` or `thread` entrypoint in `openai/ui` metadata and supplies a `ui://` resource. Discovery joins the live Codex tool inventory with installed, enabled plugins: ownership comes from `server.pluginId` or the connector/server ids in `plugin/read`, never display-name matching. The desktop rail exposes only `global` entrypoints, using tool/server/plugin icon metadata, and navigates immediately to `/apps/:appId`. This route serves rail clicks and deep links, showing connection progress and retryable errors before opening the shared app panel expanded on its normal conversation route. The conversation replaces the loading history entry so Back returns to the previous page. Leaving the loading page abandons its launch; any late app connection is released without changing the user's new route. Each account link retains its own identity. Discovery is gated by the provider descriptor, native platform capability, and local IPC transport. The shared query refreshes after plugin mutations and when the window regains focus; ownership metadata is cached until plugin changes. `mcp-app-extensions.ts` contains routing, logical rail pin identity and its shared limit, and vendor compatibility behavior, not a plugin allowlist.

The App options menu lists every available global entrypoint; no app is automatically pinned. Opening an app and toggling its pin use separate controls. Users can pin up to five apps in pin order, with logical pin keys persisted per provider in `appSettings`, independent of mode and workspace. A versioned pin key uses `pluginId + tool.name`, falling back to connector ownership and then server ownership when plugin metadata is unavailable; it excludes account link ids, display names and UI resource revisions. App routes, sessions and remembered conversations retain their full connection identities. Rail clicks resolve a pin against the current inventory, retaining the panel’s account when still available and otherwise using the first available link; account-specific menu rows still open their own live entry. Multiple links for one logical app share one rail slot and pin toggle. Persistence version 4 carries old connection ids into the new preference field; live metadata then reconciles and deduplicates them in original order, even after a link has changed. Unresolved legacy pins are retained without guessing another plugin or renamed tool. Unpinning keeps the app in the menu and does not fill the empty rail slot. Unavailable apps are hidden without clearing their preference during inventory refreshes; explicitly pinning another app drops unavailable ids so they do not reserve slots. The options button and its divider are absent when no global apps are available. Home is inactive while the shared MCP App panel is visible, both docked and expanded, even though its conversation remains on the workspace route. Clicking Home first closes the app panel or cancels its pending launch, then runs normal Home navigation; when already on a workspace route this reveals the existing conversation and opens its sidebar without creating a chat or releasing the app session.

Entrypoint icon discovery retains tool/server icons and the owning plugin's composer, logo and dark-logo alternatives. The renderer prefers a theme-compatible SVG, recognizing MIME metadata, SVG URLs and SVG data URIs; failed images fall back to another supplied asset before the generic plugin icon. Rail icons inherit the navigation button's current color. Supplied SVGs and transparent logos use an SVG color filter; Figma, Canva, Shopify and tldraw have monochrome rail artwork for their raster catalog logos. This artwork table does not control app discovery, and panel headers keep their supplied logo treatment.

**app extension session**:
A temporary MCP connection outside a model run. `codex-mcp-apps.ts` owns an idle ephemeral app-server thread and allows only that app's UI-visible tools from the same connector/account. The desktop `mcpApps` service registers its HTML; `McpAppDisplay` hosts it using the standard MCP Apps bridge. `McpAppPanelProvider` owns one persistent document: docking, expanding and brief close/reopen cycles retain its iframe and bridge. After two minutes hidden, the panel requests graceful teardown (up to 1.5 seconds) and unmounts the app. Reopening recreates the bridge with the same conversation, host composer draft, model context and app-provided widget state. Arbitrary unsaved state inside an iframe is not serializable by the host; apps must save it through widget state or their teardown handler. Replacing the document or closing the window releases its session. Opening an app starts no model turn. Rail apps bind to a remembered normal run or a new normal composer in the current mode and context. Developer drafts capture the selected workspace; Work/Chat drafts capture the selected collection or remain general. That scope stays fixed until New chat, and opening an app never changes mode.
`useMcpAppConversation` binds the normal workspace sender and observes fresh completed MCP App results. Chat tools open the app docked, leaving an Open app button in the transcript; another result for the same server, resource, connector and account updates the current document. Historical rows only open on explicit user action. Expanded apps portal the normal floating overlay, composer, transcript and approvals over that same document; docking restores the main conversation. App previews share the browser's toolbar controls, slide transition and resize range. Rail opening and expansion show the compact composer first; New chat reveals it if hidden. Opening a closed app from the transcript starts docked regardless of its previous expanded state. Explicit Reload rebuilds the UI while retaining its app connection and conversation. The remembered run is scoped to backend, space, provider, mode and the app's full connector/account identity. The app connection remains distinct from the conversation. Tool-originated documents retain their source run for resource access and UI tool calls even when the conversation changes; bare `codex_apps` UI tools resolve against the entrypoint's connector namespace. A new app workspace mounts only after its owning conversation makes the panel visible; an already started workspace stays mounted during the hidden grace period. Bridge startup waits for the iframe browsing context, retries briefly and reports a readable error after ten seconds instead of abandoning initialization. The iframe starts on inert `about:blank` and navigates to its registered resource only after the host transport is attached; a fabricated protocol URL creates a Chromium error document and can leave a subsequent app navigation blank. Only the actual app document’s load receives bootstrap globals and the compatibility fallback; the placeholder load does not. Callback updates, draft-to-run transitions and display-mode changes do not rebuild the bridge or iframe. The compatibility shim’s ready signal is tracked independently from the standard MCP handshake. Each channel receives the latest tool input and result when ready, and subsequent changes reach the existing document without Reload or replaying widget-state bootstrap; compatibility readiness does not enable standard RPC notifications or teardown.
The native browser floating chat is a separate renderer. It receives only an app opener that relays explicit and newly completed tool results to the main renderer over the existing browser-chat action channel. The parent checks the current composer owner and run before opening its shared app panel. Transcript launchers never mount an app iframe, including when no panel host is available.
App text messages open a host-owned editable preview before sending, for both standard `ui/message` and the ChatGPT compatibility surface. Only the user's Send action submits the edited text through the normal conversation path; Cancel, Escape, navigation and RPC cancellation while awaiting review submit nothing and report an unsuccessful message result to the app. Typed composer messages still send directly. App text messages use the current conversation by default. An `openai/message` request with `target: "new"` creates another real run while retaining the same app connection. Failed or duplicate sends are reported to the app instead of being acknowledged as sent.
Opening reuses one live inventory for ownership validation and tool scoping. Rail, connector overview, and plugin runtime reads share concurrent MCP inventory requests, with a 60-second discovery budget; settled requests are discarded, and plugin changes/server shutdown invalidate pending reuse. Explicit resource targets belong only to `codex_apps`. Synthetic link ids request the protocol's no-auth target (`linkId: null`), subject to the app's resource policy; the original link identity still scopes allowed tools.
_Avoid_: fabricating run rows for standalone apps; borrowing another run's MCP thread; allowing an app to call a different connector or account; putting Electron protocol code in the shared backend.

**app conversation context**:
`ui/update-model-context` replaces the canonical composer's `mcp-app` items for that app instance. Content blocks become individually removable chips; assistant-only blocks and structured context remain background context. `mcp-app-context.ts` bounds and validates the payload, keeps presentation metadata out of model input, maps images to actual attachments and sends text/resources/structured data through the common run-context builder. The host acknowledges an update id and notifies the app when attachments change or clear. An in-flight send consumes only the submitted snapshot, preserving newer selections and draft edits. New model tool results for the same server, resource, connector and account update the permanent app without replaying historical bootstrap grants; UI-only result metadata stays on the UI bridge.
_Avoid_: a separate attachment store or custom run-start flow for apps; clearing new selection updates that arrived during send; sending tool-result authentication metadata as model context; reconnecting the canvas when only the conversation id or callbacks change.

**app document origin**:
Each document gets a distinct `mains-mcp-app://<uuid>` origin, separate from Mains and other documents. The sandbox permits same-origin storage for canvas libraries while the document's CSP limits network/resource/frame access. Browser identity headers omit Electron product tokens; authentication and Origin headers are preserved. Vendor origin allowlists remain authoritative: as tested on 2026-10-01, tldraw's UI loads and MCP calls succeed, but its live sync rejects the Mains origin with 403. The preview returns an explicit host compatibility error for `_dotcom_zero`, allowing tldraw's own MCP file-list fallback. Known Figma validation and tldraw sync limitations use the app's neutral top toast instead of an inline banner. The shared panel provider owns the notice across the loading route and both panel sizes. It waits 800 ms before showing it, cancels a pending notice when the app is left, and uses the normal toast entrance and exit transitions. It has no expiry, supports Dismiss and Escape, and is removed when the app is no longer shown. A dismissal survives metadata updates, Reload and reopening that entrypoint within the same backend/space/provider/mode context. These unsupported interfaces have no floating chat host, and their expanded toolbar keeps Reload without Restore; docked tabs retain Expand and Close. Plugin tools and the normal conversation remain available. Dismissing the notice does not enable the unsupported interface, and ordinary connection failures are not classified as origin restrictions.
_Avoid_: sharing Mains' origin with third-party HTML; pretending to be an OpenAI or vendor origin; stripping Origin to work around a vendor refusal; disabling browser security.

## Provider variants

Renderer-side vocabulary for the workspace UI shared across the four agent providers, all hosted on the single `/code` route.

**provider variant**:
The renderer's short identifier for one of the four agent UIs — `claude | copilot | codex | cursor`. Distinct from the **ProviderId** DB key (`claude_code`, `copilot_cli`, …); the **variant descriptor** maps between them. The active variant comes from the active space's `providerId` column (`useSpaceProviderVariant`), not the pathname — the space picker is the only way to switch providers. `WorkspaceVariant` additionally includes `default` (returned by `useWorkspaceVariant` off the `/code` route), which callers narrow to a variant before use.
_Avoid_: re-declaring the `"claude" | "copilot" | "codex" | "cursor"` union inline — import `ProviderVariant`.

**variant descriptor**:
The single renderer-side table — `src/renderer/lib/provider-variants.ts`, keyed by **provider variant** — holding each variant's `providerId`, `icon`/`accentClassName`, and capability/config facts: `permissionKey`, `permissionDefault`, `effortKey`, `thinkingCoupledToEffort`, `fastMode` (`boolean` vs Codex's `serviceTier`), `supportsUltracode` / `supportsPlanMode` / `supportsGoalMode` / `supportsSkills`, and the `/code` page wiring (`planExit`, `enableForkRun`, `enableSuggestions`) that used to live as per-route props. Components and `use-provider-models` read fields from it instead of branching on `variant === "..."`. The config-key fields mirror what the main-process drivers read (codex → `sandboxMode`, `modelReasoningEffort`, `serviceTier`; cursor → `mode`; claude/copilot → `permissionMode`) — a contract shared across the process boundary even though only the renderer branches (each driver hard-codes its own keys).
_Avoid_: re-deriving a variant's icon, provider id, config key, or capability with an inline `variant === "..."` ternary; duplicating the variant↔providerId mapping (use `getProviderVariant(variant).providerId`).

## Composer context

Inline composer mentions open their attached resource: files use the existing editor navigation, plugins use `/plugins?provider=…&plugin=…`, and skills with a `SKILL.md` path open the Markdown document viewer. The shared rich input emits chip activation callbacks and keeps prompt serialization unchanged. Provider skill discovery registers exact resolved `SKILL.md` files as readable content, so global skills can be viewed without granting access to their directories or adding write access.

The rich composer serializes Markdown for submission, while suggestion detection reads visible text up to the caret with chips and literal code/link regions treated as boundaries. Markdown paste and restored drafts end with an ordinary continuation line, so further typing can leave the last list, heading, quote or code block.

**conversation settings**:
The model, effort, permission and other composer toggles belong to the conversation owner (`composerOwnerKey`), including unsent drafts. New chats inherit the last-used model, effort/thinking, permission and fast-mode preferences for their backend and provider; Plan and Goal start off. Successful starts/resumes and selection changes in an existing chat update these local defaults. Opening an older chat does not replace them, and unsent draft changes become defaults only after a successful start. Provider settings supply the fallback before any run preferences have been remembered. Existing chats persist their next-message preferences in `runs.configSnapshot.conversationSettings`; the flat snapshot still records the settings applied to the current or last execution. Editing the composer does not change an active turn. Start, resume and fork apply the conversation preferences before the mode harness enforces its restrictions. The renderer persists draft settings and last-used new-chat defaults locally; existing chat preferences reload from the backend. The native floating chat mirrors the parent's settings and relays changes with its owner key. Queued messages capture settings with their other input, without replacing newer composer preferences when delivered.
_Avoid_: writing composer selections to the provider row; using a provider-wide model selection when returning to a chat; changing the initial `runs.model` snapshot to remember a next-message preference; persisting provider credentials as conversation settings.

Catalog model fallback and effort clamping carry an `automatic` change source, including through the native floating-chat relay, and update only the conversation. Explicit selections and starts receive a renderer-local revision per backend/provider; remembered defaults accept successful results in that intent order, so late responses cannot replace newer choices and a rejected newer start does not discard an older successful fallback. Revisions are not persisted. New conversations requested directly from an existing chat reset Plan/Goal in both the request and composer settings; deliberate toggle choices in a new draft are preserved.

**reasoning effort**:
An identifier advertised by the selected model, not an app-wide enum. Codex's `model/list.supportedReasoningEfforts` is the source for its picker; conversation settings, paired-device settings and Pulse preserve that string unchanged. Mains validates the setting's type and the renderer clamps selections when switching to a model that does not advertise them. The app-server validates the model/effort pair at execution. `EFFORT_LEVELS` ranks known levels for default selection and validates other providers' fixed vocabulary; it does not limit Codex. No schema migration is needed because effort is already stored as text in configuration.
_Avoid_: hardcoding a Codex allowlist, casting its catalog values to a closed union, or normalizing its identifiers before forwarding them.

**context item**:
Anything the composer attaches to the next message besides its text — a file, a tracker issue, a signal, a skill, a browser selection, a Lens capture, or a code selection — as one tagged union in `features/workspace/lib/composer-context.ts` (`ContextItem`, `kind` intersected onto the payload so `ContextIssueItem` stays assignable to `ContextIssue`). The store holds a single insertion-ordered `workspace.contextItems`, changed through exactly three reducers (`addContextItem` / `removeContextItem` / `clearContextItems`). Identity lives in the module, not the reducers: `contextItemKey` is the removal handle (path / entityId / name / uuid) and `isSameContextItem` is the duplicate rule — the same for every kind except `code`, whose uuid is minted per capture, so two selections are the same when they cover the same span. `groupContextItems` is the per-kind view the UI renders from, returning one shared frozen instance for the empty case so downstream memos stay identity-stable. The six original kinds previously had six state fields, six add/remove/clear reducer triplets, duplicate type declarations in the slice *and* `use-workspace-runs.ts` (the second copy had already lost three fields off the browser selection), and twelve props threaded through `WorkspaceInput`.
_Avoid_: adding an eighth per-kind state field, reducer triplet, or `contextX` prop; re-declaring any `ContextIssue`/`ContextSkill`/… shape outside this module; deriving an item's identity inline instead of calling `contextItemKey`.

**`useComposerContext`**:
The read path for **context items** (`features/workspace/hooks/use-composer-context.ts`): the flat list, the grouped per-kind views, and `add` / `remove` / `clear` plus the route-reset operation that retains global Lens captures while dropping workspace-scoped context. Components render from it directly rather than receiving context as props — that drilling was the reason the lists and their removers could disagree. Explicit removal and route discard free unused browser/Lens files. A successful send only clears composer state: its source stays in the bounded capture cache long enough for the asynchronously starting provider session to copy it, then normal eviction removes it. Calling the hook subscribes to every context change, so a component that only *attaches* (file explorer, code viewer, browser panel, global Lens bridge) dispatches `addContextItem` directly instead.
_Avoid_: passing context lists or `onRemoveContextX` callbacks down as props; reading `state.workspace.contextItems` in a component instead of going through the hook.

**workspace review**:
The Changes panel opens one workspace-scoped `review` tab, with the current uncommitted snapshot rendered as ordered, collapsible file diffs. It shares the preview controls and floating chat surface; sending a message keeps the Review tab selected and targets its chosen chat. The tab and chat target live in the existing workspace view snapshot. Pending line comments are `kind: "review"` context items under the conversation owner, with no separate storage. Each captures the file path, old/new side, one-based line number, code text and patch fingerprint. A changed patch leaves the original comment in the composer attachment rather than attaching it to a different line. Comments travel through the existing selection context payload; the adapter projects validated `reviewComments` metadata onto the saved user prompt, which renders the same attachment read-only. Unsent comments disappear on reload, like pending browser annotations.
_Avoid_: treating `review` as a run id; persisting a second comment ledger; re-anchoring comments to changed code by line number alone; clearing a comment edited while a send is pending.

The Review surface keeps one diff/editor tree mounted while `use-review-panel-transition.ts` animates its docked and expanded bounds, titlebar inset and height on one clock. Interruptions continue from the visible geometry, and reduced motion settles immediately. The expanded titlebar inherits the shell's traffic-light/sidebar gap. Floating chat retargeting uses the title dropdown; the regular composer uses the same `ComposerSendTargetSelect` as a chip. Portaled Review menus sit above the expanded surface.

Native fullscreen subscriptions deliver the current sender window's state as well as later enter/leave events. Preload subscribes before reading `app:getFullscreen` and ignores that snapshot after a newer event or unsubscribe. Sidebar toggles, collapsed shell headers and expanded panel insets therefore recover their traffic-light spacing after remounts or renderer reloads; this chrome query stays local to Electron.

Review's scroll container uses Pierre's `Virtualizer` to keep only nearby diff rows rendered, including measured wrapped lines and comment cards. `ReviewDiffProvider` scopes a two-worker highlighting pool with a bounded AST cache to mounted Reviews; parsed patches carry content-based cache keys. `useComposerReviewComments` derives a shared workspace/file index from the existing context list and retains unaffected subscriptions, while `useComposerContextActions` exposes the same mutations without subscribing. These are projections of the current conversation owner's context, not another comment ledger.

The Review toolbar searches changed files by current or renamed path, with keyboard selection and at most 100 menu rows. `use-review-file-navigation.ts` commits the selected file's expansion, invalidates cached scroll dimensions and jumps instantly within the virtualizer's logical coordinates, keeping focus on its header. Native smooth scrolling is interrupted by Pierre's height-reconciliation anchor corrections as intermediate files render. The toolbar switches unified/split layout on the same mounted diff and annotation tree, preserving pending editors and old/new comment anchors; the layout choice is local to the Review surface.

**run context payload**:
The projection of **context items** onto what `runs:execute` / `runs:continue` take, in `features/workspace/lib/run-context-payload.ts`. One `buildRunContextPayload(items, uploads)` returns `initialContext` (Lens captures, browser selections, then code selections), the merged attachment list (user uploads plus Lens/browser screenshots), and the `contextIssues` / `contextFiles` / `contextSignals` / `contextSkills` wire arrays — empty groups omitted as `undefined`. A Lens capture's image and bounded accessibility text travel together here. Execute and continue previously built this inline and independently, ~30 duplicated lines each, taking the six original context arrays as positional parameters in two *different* orders.
_Avoid_: shaping run context at a call site; giving `executeRun` / `continueRun` per-kind context parameters again (they take one `ContextItem[]`).

**durable prompt attachments**:
All modes use the run service's preparation step before provider input: images, documents and inline text are written atomically under `userData/attachments/<attachmentId>/<filename>`, verified, then retained through `run_attachments` and `run_attachment_refs`. Storage keys are relative to the data directory. Provider requests receive the original's path; saved user prompts contain only `attachmentId`, name, type, MIME type and byte size. Same-name files have distinct identities, and queued message ids make uncertain delivery retries reuse the original. Forks retain the source run's attachment references before native session acquisition. Archive keeps originals; deletion releases references and removes an original only after its last run is gone. Startup cleans abandoned files after 24 hours. Backups/restores must include the database and `attachments/` together; thumbnail caches are disposable.

Image reads validate both conversation and attachment identity over the shared backend transport. Transcript tiles request 256px JPEG thumbnails, visible desktop tiles hold Blob URL leases, and expanded previews request at most 1600px and release their URL on close. The thumbnail LRU targets 64 entries / 16MiB in clients and 128MiB on disk; one backend decode queue prevents simultaneous large decodes. Electron uses `nativeImage`; the standalone Node host supplies Sharp with a small native cache. Downloading explicitly fetches original bytes, independent of preview resolution. Only newly sent attachments use this storage, including those sent in existing conversations. Existing prompt metadata stays unchanged and its legacy presentation remains supported; startup maintenance never scans or converts old prompts.
_Avoid_: base64 or absolute host paths in new prompt metadata; adapter-owned temporary upload copies; previews that fall back to original bytes; deleting originals on archive or transcript-row removal; accepting general file paths from paired devices.

**local run queue and steering**:
Codex exposes `supportsTurnSteer` through its variant descriptor. During an active response, empty input offers Stop; text, uploads or explicit context can enqueue a message. The unpersisted `runQueue` slice stores FIFO snapshots under `runOwnerKey(backendId, runId)`; File bytes and previews stay in the transient upload store. One app-level consumer executes queued continuations after normal completion, including while their tabs are unmounted. Stop, failure, archive, disconnection and backend changes pause delivery until explicit resume. Editing keeps the message's id and position and temporarily backs up the current draft, context, files, conversation settings and directories. The native floating chat mirrors the parent's queue and relays actions; the parent owns delivery.

Queued rows show one representative image thumbnail or file icon beside their text, including for multiple attachments. Dragging the hover handle (or Alt+Arrow) changes the local FIFO order while preserving message ids and upload owners. Stale permutations are ignored, and editing, sending or uncertain delivery lock sorting. Delivery selects the current head after status preflight, so a reorder while that read is pending takes effect before input is sent. Native chat mirrors only small cached thumbnails and relays sorting to the parent.

Steer adds one queued snapshot to the existing parent turn through `turn/steer`, with a captured `expectedTurnId` and no model or directory overrides. Accepted input is correlated by `clientUserMessageId`, persisted once in the existing user-prompt artifacts, and does not open another turn or Git boundary. Lost responses keep input locally until native history confirms acceptance; they never trigger automatic resends. Queue state disappears when the app closes or reloads.
_Avoid_: database migrations or persistence for pending messages; a consumer per composer mount; steering a subagent or a subsequent turn; removing files before acceptance; acknowledging delivery from a running-status event alone.

**browser annotation**:
One browser **context item** with an `elements` array and shared `comment`. Its top-level element fields retain the first selection for compatibility; an ordinary browser screenshot has no `elements`. `shared/browser-annotation.ts` holds the structural element wire type used by main and renderer. The injected inspector keeps multiple DOM selections and their outlines inside an isolated shadow root, blocks guest page actions, and captures a highlighted viewport after hiding its comment editor. Add delivers one PNG plus every element's own selector, text, coordinates and optional component/source identity, then clears the group while leaving annotation mode active. The composer presents all groups under one annotation/element count, with screenshot preview, comment editing and group removal. Comment edits reuse keyed context replacement and retain the captured file. An empty main prompt can send the annotation comments; an edit made during send remains in the composer for the next message.

Sent user-prompt artifacts retain a compact `browserAnnotations` array for that message, projected from its selection context in the shared provider lifecycle. The transcript renders screenshots, a count chip and read-only element/comment details, independent of the current composer. Image attachment metadata uses the durable attachment identity so historical previews survive transient capture-cache eviction. Composer and transcript share the element/comment presentation. Annotation dropdowns do not suppress the live browser; full-window overlays acquire unique main-owned suppression leases. Releasing a lease respects the panel's attachment, requested visibility and every other renderer's leases, so closing a preview cannot reopen a closed panel or reveal a page on Settings.
_Avoid_: a separate annotation state list or run-start path; treating each selected element as an independent attachment; borrowing the first element's component/source metadata for another element; capturing the comment editor in the annotation PNG.

## Lens

**Lens capture** (internal kind `appshot`):
A local macOS snapshot of the frontmost app window, captured by `main/modules/appshots` through Electron's `desktopCapturer` and paired with a bounded accessibility-text snapshot when the user has granted Accessibility permission. The global accelerator is persisted in `app_settings`, registered only in the desktop main process, and exposed through local Electron IPC rather than the WebSocket handler registry. PNGs share the main-owned `userData/browser-captures` trust boundary and `mains-capture://` renderer protocol with browser inspector captures. `use-appshots.ts` turns a delivered capture into an `appshot` **context item** and navigates to the composer; capture never executes or continues a run by itself. User-facing configuration lives on the standalone Settings › Lens page; `appshots` remains the internal module, IPC, type, and storage name.
_Avoid_: putting Lens controls back on General; registering Lens on the remote backend transport; sending a capture directly to a provider; reading screen or accessibility content before an explicit shortcut/button action; accepting renderer-supplied source paths outside the trusted capture directory.

## Transcript rows

**structural plan snapshot**:
The live execution checklist emitted as a shared `plan_update` adapter event. `RunSession` merges the latest snapshot into the active `run_turns.metadata.codexPlan` value and emits the normal `runs:eventPersisted` invalidation, so tab focus and reload recover the same state without replaying transient notifications. The renderer validates that metadata and gives it precedence in `TodoSummaryBar`, falling back to legacy `UpdateTodos` or `TaskCreate`/`TaskUpdate` tool-call aggregation for providers without structural plan events. This is distinct from a plan proposal rendered by `PlanDisplay`, which is content awaiting Apply/Dismiss.
_Avoid_: storing live plan progress as fake tool calls; replacing the whole turn metadata object; treating a proposal `plan` item as execution progress; keeping structural plan state only in component memory.

**turn changes**:
What one agent turn did to the working tree, stored in `run_turn_changes` (one row per turn, owned by the `runs` module) and drawn as the transcript's "Edited N files" card (`turn-changes-card.tsx`) beside the turn's session bar. `RunSession` takes a **working-tree snapshot** — `gitService.snapshotWorkingTree`, a git tree object written through a throwaway index, tracked + untracked with `.gitignore` honoured, HEAD/index/files untouched — when a turn starts and when it closes, and `gitService.diffTrees` turns the pair into a complete patch (binary hunks included) plus per-file stats. At an in-session boundary one snapshot is both the closing turn's end and the next turn's start; a new session (continue, fork) takes a fresh baseline, so edits the user made between runs are never attributed to the agent. The complete patch is stored in SQLite, not kept as git refs, so large and binary-file turns remain undoable and the record outlives the repo, its worktree, and gc; the trees themselves are unreferenced and left to git. The summary rides along on `RunTurnResponse.changes`; the patch loads only on Review (`runTurns:getChangesDiff`). Snapshots are provider-agnostic (edit tools, shell commands, and codegen all count), so on their own they cannot say whose hand made a change. The **worktree writes** ledger (`git/worktree-writes.ts`, in memory, keyed by the worktree root, kept only while a session is live) sorts them. Every session records the files its tool calls named (`toolWrites` in `adapter.shared.ts`; a shell names none), and the app records what its own operations wrote — pull, branch switch, discard, turn undo (inside the `gitService` methods that do them) and an editor save (`fileExplorer.writeFileText`) — through `noteAppWrites`. When another run was live in the worktree during the turn, or the app wrote to it, the closing turn (`attributeTurnFiles`, `runs/turn-attribution.ts`) keeps the files its own tools named, plus the files nobody named if it ran a shell — never a file only someone else named — then re-diffs the pair narrowed to those paths so the stored patch holds only its files. A kept file someone else may have written too is marked `shared`: its hunks can't be told apart. A turn nobody else touched keeps every change, as before; the integrated terminal and outside editors name no files, so their writes still land on the card. **Undo** (`runTurns:undoChanges`) reverse-applies the stored patch — refused while the run is live, for legacy rows whose patch was already truncated, for a turn with a `shared` file, or when `git apply --check` fails because a touched file moved on; `git apply` is atomic, so a refusal writes nothing. Two shells' writes in one worktree still can't be separated (such files are kept and marked `shared`), and a working tree over the untracked-file guard (5k files / 100MB) gets no card.
Workspace Activity projects one file-change event per `run_turn_changes` row, including its undo state. `workspace_activity` still owns commits, reviews, and other timeline events; its old run-end diff events appear only when the run has no turn-change rows. The run-final diff snapshot continues to serve the current Changes view but no longer writes file-change activity.
_Avoid_: using a provider's own turn-diff events as the source; persisting snapshot trees as git refs; putting the patch in `run_turns.metadata` (turns re-sync on every event); reusing `workspace_diffs`, which holds the workspace's current uncommitted diff, not history; undoing by re-checking-out files instead of reverse-applying the patch; attributing a parallel run's files by time alone (they write while this turn is open); keeping a file only someone else named; recording an app write at each call site instead of in the operation that writes; giving the scratch index a fresh mtime (git's racy-clean check reads it, and a same-size edit in the index's second would vanish).

**transcript rows**:
The pure (React-free) layout plan for the run transcript, in `features/workspace/lib/transcript-rows.ts`. Two public functions consumed by `workspace-events.tsx`: `buildTurnRenderRows(groups)` keeps speech and native voice tools in chronological `flat` rows and preserves regular text `accordion` rows (with plan tool groups and image/document artifacts broken out so they stay visible), and `matchTurnsToGroups(groups, turns, …)` decides which group index each session-time bar attaches to. When one agent turn emits several revisions of the same logical document, only the newest revision breaks out; older revisions remain recoverable inside the collapsed accordion. Everything else in the module (`partitionAgentTurn`, `collectResponseContent`, `computeSessionTimesFromEvents`, …) is an internal seam — used by the module and its tests, not exported. The module is the test surface for transcript layout, which previously could only be exercised by rendering.
_Avoid_: re-introducing turn-grouping / accordion / session-bar math inside `workspace-events.tsx` (it is presentation over `buildTurnRenderRows` / `matchTurnsToGroups`).

## Run cache

**session resources**:
The compact Sources/Deliverables shelf inside `features/workspace/components/session-panel/`. It is a read-only projection, not a fourth run ledger: `session-resources.ts` derives sources from `run_context`, structured `user-prompt` artifact metadata, conversation links, and web-tool inputs, then derives deliverables from output artifacts plus visible files in a Work/Chat run's managed execution directory. The filesystem pass catches Write, shell, and provider-native output that emitted no artifact; it is bounded, skips symlinks/hidden files and the managed `collection-sources` link, and never scans a Developer workspace. It also correlates prompt-attached `scope: "plugin"` identities with persisted MCP tool calls, so only plugins actually invoked during the run appear, deduped with a call count and their persisted brand treatment. Canonical path/URL identity collapses repeated sources; document family identity collapses punctuation and draft/render/final variants per format, while scanned office-render sidecars (`fod*`, OpenDocument, HTML, SVG) disappear when their final document is present. The newest logical document wins, while an explicit artifact remains authoritative over a discovered file with the exact same name. Code combines Sources with the workspace Environment; Work shows Sources and, when present, Deliverables even for workspace-less runs; Chat does not expose the panel. The section fetches only while open and listens to the shared coalesced `runs:eventPersisted` signal while a run is live.
_Avoid_: copying these rows into a new table; mixing agent outputs into Sources; treating document-render preview images as separate deliverables; scanning a Developer workspace as output; showing the `.mains` source snapshot as a deliverable; querying git for a workspace-less Work run.

**git actions panel**:
Message generation is a separate one-shot provider call, fed by Git data and project instructions (falling back to app instructions), without the session transcript or its selected model. Commit prefill uses `gitService.getCommitPreviewDiff`: staged-only when requested, otherwise `captureDiffSnapshot` against HEAD (the empty tree before the first commit), including untracked files without changing the index. PR generation uses the chosen base's three-dot diff and every commit subject in `base..HEAD`, with no commit-count cutoff; if no base can be read it uses the working-tree preview without unrelated repository history. Diffs in generation prompts remain capped at 100,000 characters.

The git menu inside the session panel, in `features/workspace/components/session-panel/git-actions/`. Six rows — changes, branch, commit, pull, PR, publish — each its own component, opening in place rather than swapping the panel's contents. Five own their form state; pull owns none, because it takes no input and so gets no form between the click and the only thing it can mean. The branch row carries two: the checkout it names, and a `+` action that opens the new-branch form under it (a `pinned` hover action, so the toggle it becomes stays visible while that form is open). `useGitActionsPanel` holds only what more than one row needs: the `getGitFlowStatus` query and the `refreshStatus` every mutation funnels through, the accordion (commit and PR are mutually exclusive; the rest stack), the single `pending` action that makes the others `busy`, and the working-tree facts defaulted in one place (`hasRemote` defaults to *true* until status loads, so a normal repo never flashes the Publish flow). A row that turns unusable closes its own accordion — `refreshStatus` re-checks each open section against the fresh status, because a disabled row can't be clicked shut. Publish replaces PR when the repo has no remote; push, pull and PR are impossible until it does. Pull is `--ff-only` and always runnable when the branch has an upstream: `behind` is only as fresh as the last fetch, so it decides what the row *shows*, never whether it may run — pulling is how that number becomes true.
_Avoid_: putting a single row's form state in `useGitActionsPanel`; gating Pull on a `behind` count; refetching status without going through `refreshStatus` (the accordion would keep a dead row open); adding a second in-flight action alongside `pending`.

The PR description has Markdown Write/Preview views and a selection-aware formatting toolbar. Image/video Files and preview URLs stay in the PR row's disposable renderer draft, surviving compact/modal moves and failed creation; removal, successful creation, backend change and unmount release their URLs. Paste, drop and picker additions replace the saved selection (or the enclosing template comment) with opaque `mains-pr-attachment:` Markdown destinations; each attachment can be inserted again at the cursor. Selection survives compact/modal moves. Images remain in comparison-table cells; video links remain in the cells with a standalone player below the table. Removing media removes its generated references. Preview resolves draft destinations locally and sanitizes HTML, including existing GitHub `<img>` tags with width/height. Create stages media in 1MiB chunks on the captured transport and maps draft identities to upload identities. The backend owns private temporary paths scoped by workspace, accepts only supported media within the GitHub limits and rejects missing references before push. It maps references to encoded staged paths; `gh pr create --attach` rewrites Markdown references to uploaded GitHub URLs in place and appends only unreferenced media. Local raw-HTML media references are rejected because gh does not rewrite them. `--body-file` preserves the complete Markdown. Attachment and body files are removed after the attempt, with idle upload expiry as a fallback. An unsupported CLI fails before push. A CLI failure that returns the created PR URL is success with a media warning, so the form closes instead of offering to create it again. Remote PR creation with media has a ten-minute response window rather than the ordinary thirty seconds.

**run hook seams**:
Live assistant reports have a message-scoped stream identity even when a provider reuses its native block id. `RunSession` retains their latest snapshots, retires them when the final artifact is saved, and persists remaining prose (marked `interrupted` on cancellation/failure) before publishing terminal status. In-flight final-message inserts finish before this recovery to avoid duplicate artifacts. The renderer settles these previews on terminal status and keeps them until history acknowledges their stream identity; only transient thinking/tool/plan previews clear immediately. Interrupted reports keep unfinished math suppressed after the reveal buffer drains.

`use-workspace-runs.ts` holds the run list, the selected run, each run's transcript, and how both load. Two subjects are delegated because neither is about *holding* that state, and both reach back through the same three callbacks (`registerNewRun`, `loadRunDetails`, `onRunUpdated`) — that trio is the entire contract. `use-run-operations.ts` owns starting/continuing/forking/reviewing plus the `canResume` probe, and owns `isLoading` / `error` with it (they describe an operation in flight, and nothing outside sets them). `use-run-sync.ts` owns keeping a run in step: the transcript push (scoped to the selected tab, including idle voice transcripts, debounced), the status push (scoped to any open run, so a backgrounded tab can't miss its terminal event), the 10s polling fallback for running work, and the `finalizeRun` all three funnel into — idempotent through the **run cache**'s finalized set, re-armed by each new running notification.
_Avoid_: widening the three-callback contract into passing raw setters; putting a run's API call in `use-workspace-runs.ts` or a listener in `use-run-operations.ts`; reporting a terminal status outside `finalizeRun`.

**history window**:
Text submission has an immediate, disposable renderer projection in `use-submitted-prompts.ts`, scoped to the backend/view and composer owner before a run exists, then to the returned run id. `clientPromptId` travels through ordinary execute/continue into the saved prompt metadata and replaces this projection by identity; repeated text is never a match. This display identity does not opt into Codex queue/steer acceptance (`clientUserMessageId`). A rejected request keeps the composer draft and attachments; a session that fails before persisting its prompt keeps the local message with the failure visible. Registering a new run reads its first history page immediately, and transcript sync subscribes before its catch-up read so early pushes do not force a wait for polling.
`runs:getHistory` serves a transcript window for Chat, Developer and Work, shared by desktop, standalone web and mobile. Opening reads the last 10 user-prompt blocks; older/newer requests move by 10 and retain at most 30 blocks. Boundaries use displayed time, source and row id, including `voiceStartedAt` for delayed voice persistence. Only navigation keys are examined outside the window; historical message/tool bodies are read within it. Runs without prompts use blocks of 20 events. The complete database and provider context remain unchanged; no history migration or startup rewrite is needed. A block can itself contain a large message or many tool calls, so the limit is by blocks rather than bytes.
`use-run-history.ts` owns desktop window data and metadata. Paging and refreshes serialize per run; clearing or forgetting a view invalidates late responses. Scrolling away from the tail freezes the upper edge while live work continues. `use-transcript-scroll.ts` restores a stable visible row's position after page replacement, and explicit latest requests land at the tail. Rows use event identities rather than page-local indices for keys. Sending a continuation returns to latest. Mobile replaces only its disposable SQLite projection of that run in a transaction and preserves its visible turn's position; before remote sync, offline queries cap old caches at 200 rows per source. The automatic subagent navigator requests only spawn/continuation rows and excludes tool outputs, so it cannot inadvertently materialize the full tool history behind the paged transcript. Explicit resource/detail surfaces retain their full-history reads.
_Avoid_: growing arrays across every visited page; applying an older live response over a newly selected window; following live streams in a historical window; scrolling to the end after prepending; treating a turn-count limit as a byte budget.

**transcript viewport and tool payloads**:
`TranscriptWindow` keeps thin measured row placeholders for history anchoring and the turn rail, mounting only visible bodies plus a viewport buffer. Inactive transcript tabs unmount their bodies. A four-view cache retains only scroll offsets, row heights and bounded accordion values (128 heights and 512 interaction values per view); it holds no events, DOM nodes, media or tool payloads. Tool groups and closed detail bodies unmount; individual detail bodies retain the 200ms closing animation first. Prompt block paging still bounds the data itself.
Tool events keep raw input/output in metadata and only a bounded input preview in `content`; the former formatted/parsed duplicate is removed. A fetched page is mapped once before reconciliation. Generic/MCP/command detail formatting happens inside mounted detail bodies. Generic large bodies show a preview with an explicit full-content action. Desktop history requests may defer completed Read/Bash/Shell outputs larger than 16k characters: SQL returns a 2k prefix and length without loading the full result into backend JavaScript or IPC. `runToolCalls:getOutput` reads the original output only for its owning run when the row expands, and the row releases it after closing or leaving the viewport. Pending tools, MCP app results, mobile history and provider context retain complete payloads.
Atlas Page tools retain their native provider names and result envelopes in history: Claude's `mains` MCP server namespaces them as `mcp__mains__AtlasReadPage`, while Codex dynamic tools use bare `AtlasReadPage` names. The UI resolves exact Read/Create/Update Atlas names before generic MCP and substring-based file-tool matching, including historical rows. Their dedicated Read/Create/Update displays unwrap Claude `text` and Codex `inputText` results into the same Page projection. They show named request fields, title/version transitions, rendered Markdown or inert BlockNote content previews, and explicit read/save/create outcomes or errors; they never route through the generic JSON display. Content bodies mount only on expansion and large content needs an explicit full-content action. Group summaries describe Atlas page operations and distinguish failed attempts from completed changes.

**browser live views**:
Closing the final tab in the current conversation detaches and closes the browser panel without creating a replacement tab. The renderer handles both explicit close responses and native shortcut state updates; entering a different conversation with no tabs does not count as closing its final tab. Reopening the panel creates its normal blank tab on attachment.
The browser targets at most three live views, including its active tab, hibernating the least recently used inactive tabs. Audio-playing/loading pages and pages that veto `beforeunload` remain live, so the limit is soft. The existing two-minute hidden-panel timer uses the same guarded hibernation. Chromium's current-page state plus a supplemental text/form/scroll snapshot stay only in a bounded 8MiB session cache and are passed to navigation-history restore on wake; disk persistence still contains URLs/titles only. Selected file inputs, oversized forms and failed captures keep their view alive. Supplemental state restores ordinary inputs, textareas, selects and editable text without storing passwords. Form restoration remains best effort for custom application controls; arbitrary application JavaScript state requires the page's own persistence. Clearing browsing history also clears suspended state.

**run cache**:
The framework-free bookkeeping state machine in `features/workspace/lib/run-cache.ts` (`createRunCache()`). It owns the four-run LRU, loaded flags, finalized set, and coalesced live-refresh bookkeeping. `useRunHistory` prunes event, turn and navigation maps to the same whitelist. Evicted runs reopen on a fresh latest page. `tryAcquireLoad` / `clearPending` / `hasPending` / `releaseLoad` coalesce repeated sync triggers; the history hook serializes these with navigation requests. `pruneRunMap` preserves the map reference when no eviction is needed.
_Avoid_: retaining window metadata after its events are evicted; fetching the complete transcript on a cache miss.

## Pull request inbox

**PR view model**:
A pull request row served by the `pullRequests` module (`pullRequests:search` / `pullRequests:getAvailability`) for the `/tasks` screen. PRs are **live view models, never entities**: CI status, mergeability, and review state go stale too fast for the sync path, so the module queries the provider per request (GitHub GraphQL `search` via the stored connection token) and persists nothing. The synced `github:pull_requests` fetcher still exists for entity-backed surfaces (pulse/signals), but the PR inbox never reads entities — one screen, one source of truth.
_Avoid_: writing PR rows into `entities`; rendering the PR tab from synced entity data; adding a DB table to the `pullRequests` module.

**PrSource**:
The per-provider interface (`pullRequests/sources/source.types.ts`) behind the PR inbox — reads (`getViewer`, `search`, `getDetail`, `getDiff`) plus write actions (`merge`, `markReady`, `addComment`, `addReviewComment`, `replyToReviewThread`, `resolveThread`). Search scope defaults to the connection's selected repos (`getSelectedResources`, the set issue sync uses); under that scope the `all` relationship means "every PR in those repos", not `involves:@me` — mirroring the sync module's `ResourceFetcher` seam: one file per provider, `source.factory.ts` resolves provider id → source using `getConnectionWithSecrets` from the connections barrel. GitHub is the first implementation; GitLab/Bitbucket slot in as new files behind the same interface. Sources are constructed per call (no cache) so a token change is picked up immediately.
_Avoid_: provider `if`/`switch` branches in `pullRequests.service` beyond the factory; importing connection crypto helpers (call `getConnectionWithSecrets`); shelling out to `gh` for inbox reads (the token path works without the CLI installed).

## Flagged ambiguities

- "ServiceResponse" was historically defined ~27 times across `src/main/modules/*/dto.ts` in two structurally incompatible shapes (discriminated union vs optional-fields object). Resolved: the discriminated union is canonical; every module now re-exports the canonical type (no remaining bespoke envelopes).
- `sync` previously carried partial `SyncJobResult` data on its failure branch. Resolved: `success` now means "the orchestration completed" (per-item failures live in `data.errors` count), `fail("Sync job failed")` only when the orchestration itself throws. The information that used to live on the failure-branch data was a misleading "errors=1, total=0" placeholder; nothing real was lost.
- `space` previously carried per-field validation errors as `errors: Record<string, string>` on its failure branch. Resolved: validation errors are flattened into the `error: string` as `field: message; field: message`. No renderer consumed the structured map; behavior is preserved at the user-visible boundary.
