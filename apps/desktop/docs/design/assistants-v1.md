# Assistants V1

## Scope

Assistants have a permanent identity and their own conversations, shared team memory and delegated assignments. `/assistants` owns the shared sidebar, with assistant rows only, styled like the existing workspace/chat items. The sidebar has no title, expansion arrows or nested chats. Its toolbar places New assistant on the left and a search icon on the right; search expands leftward over the action, filters assistant names/responsibilities, and clears/closes with Escape or the clear button. The navigation rail uses the shared Bot icon. Selecting an assistant restores its selected chat, defaulting to its latest conversation on first visit. The main header centers the assistant’s avatar/name profile, which toggles a nonmodal information panel on the right. Hover/focus shifts the avatar/name left and smoothly reveals a right-pointing chevron, with no layout-width change and reduced-motion support. Its background matches the main content surface and connects without a gap, with rounded top corners and the shared inverted corners at the bottom sides. The header has no conversation tabs; the right panel’s Chats tab provides history navigation. New task above an existing composer opens a fresh draft, keeping the previous conversation intact. The existing top-right browser action remains independent. Selected conversations and legacy conversation identities persist locally per backend/account/assistant, and all history remains intact. The main pane uses Mains’ ordinary transcript, rich composer, attachments and approval controls. Assistant reply prose uses slightly lighter bubbles than user prompts. Duration, copy and received-time controls reveal on turn hover or keyboard focus, remaining visible on touch. The composer starts as one row and grows with multiline input; upload/send controls stay beside the text, attachments stay above, corners remain moderately rounded, and model/focus-hint labels are hidden. The welcome/sidebar monograms open the same right information panel with Details, Chats, Memory and Assignments tabs. It reuses the shared panel animation lifecycle, keeps the chat interactive, scrolls independently, and closes with its close action, Escape or the header toggle; focus returns to the header trigger. There is no secondary name/description/action toolbar in the chat. The panel explicitly owns its theme text colors, including headings and profile values. Its shared left-edge resize handle previews width locally, saves the independent preference in appSettings on release, supports keyboard steps and double-click reset, and retains a full-width mobile overlay. Memory’s primary Add memory action sits below its introductory description. The route is independent of the navigation rail's active Space.

Avatars currently use flat, static geometric silhouettes: circle and rounded square in eight colors. The existing sphere/cube storage keys remain unchanged, and legacy circle/square values preserve their selected shapes and colors. Particle geometry, waves, gaze, blinking, breathing and visibility observers are removed from the renderer.

Creation replaces the main content pane with a centered, scrollable page form while keeping the sidebar available; Cancel restores the selected conversation. It orders avatar (static geometry, eight colors), name, responsibility, instructions, team, then provider/model/effort. It uses the desktop component library and its shared model/effort dropdown. The team picker uses the account-scoped overview. New team opens an inline form with library controls, creates through the existing team API, immediately selects the returned team and sends its id when creating the assistant. Failures keep the team name for retry. A fresh account can retain the automatic Mains team fallback; no workspace is required. The assistant freezes the selected Space’s provider/instructions plus model and supported effort. Provider/model/effort handoff remains V2.

Mode/workspace are execution context on runs and assignments. A new standalone chat is Work with its own managed directory even when the stored Space is currently Code. Code calls inherit the source conversation’s workspace or validate an explicit target. Starting a new task does not mutate an existing conversation; continuation/fork retain their own execution snapshot. Migration 0045 preserves accepted old Code jobs using their worker/profile snapshots, retains the compatibility-only legacy profile columns, and adds the avatar without rebuilding tables or deleting children.

Conversation placement follows ownership: every run with `assistantId` stays under that assistant, including Developer tasks using a repository. Workspace/recent chat queries exclude these runs before pagination. Repo execution and lifecycle ownership remain intact. The renderer filters stale list/update data and removes saved workspace tabs without archiving chats; old local Code links redirect to the assistant conversation. The ordinary requester chat remains listed under its project/workspace. The right panel provides assistant history navigation through Chats.

## Conversation history

The information panel’s Chats tab reuses desktop SegmentedTabs, Button, Text, loading spinner and glass-card materials. It shows the 100 most recently active conversations with title, last activity and a project/workspace or Work label. Selected rows expose aria-current. Clicking another chat changes the main transcript while keeping Chats open. New task selects the existing fresh draft; accepted messages keep the panel and select their new conversation without removing previous chats. Loading, retry and empty states remain within the panel.

The existing account-scoped conversations endpoint now projects mode, workspace/project names and updatedAt. Ordering uses updatedAt, createdAt and id before the bounded limit; it does not fetch transcripts or change run ownership. Unstarted welcomes retain their accepted execution and activity timestamp. Workspace/project labels are account-scoped, and archived/foreign conversations stay excluded.

## Code calls

The normal Code composer’s existing `@` dropdown lists active assistant identities. A selected assistant is a Redux `ContextItem`, with a stable selection id and human-readable chip; its payload becomes an application-origin `assistant_mention` context. The backend stamps the exact source prompt id and text, validates account/identity and carries only explicit prompt context. The durable dispatcher admits a task only after the matching real user-prompt artifact exists. Replayed contexts and reconnects resolve to the same source-run/prompt/selection assignment. Uploads travel as durable file references rather than duplicated pixels in queue JSON.

The existing queue starts a normal worker run under the target assistant’s frozen provider/model/effort and the assignment’s execution. Same-workspace effects remain serialized. A source `assistant_assignment` artifact renders a live task card with status, result, evidence and an Open chat action. Reading by assignment id keeps historical cards usable beyond the bounded overview list. The ordinary source chat can continue after reports through the existing result-delivery receipt path. Code chats expose public task tools; memory, private history and reporting remain assistant-only. Codex advertises and dispatches tools using the same mode and trusted assistant identity on start, resume, fork and realtime sessions, so assistant-only Work tools reach the domain dispatcher without broadening ordinary chat tools. Team checks still apply to assistant-to-assistant delegation.

## First conversation

Creation transactionally reserves one welcome conversation in `assistant_welcomes`. A bounded background generator uses the assistant’s frozen model and effort, with a role/profile and bounded untrusted memory references. This isolated one-shot call disables work tools, MCP, hooks and plugin settings; it creates no interactive provider session. Its application-origin setup prompt stays in the local record and never becomes a user-prompt artifact.

The first tab displays one role-specific question using the shared question control: three suggested first tasks, free text and Skip. The question and its state survive navigation and backend restart. Skip persists a friendly idle response and exposes the ordinary composer without starting work. The first real answer starts the ordinary run under the reserved identity. Its welcome is saved ahead of the real user message in the existing transcript; an application-origin context note explains the question to the native session. Other conversations start ordinary independent chats and never repeat the welcome. Existing assistants are not retroactively initialized.

Generation failures can retry text generation. A claimed answer is immutable; retries reconcile the same reserved run and never replay it under a new identity. Interrupted generation may restart safely because it has no production effects. Shutdown cancels generation and joins outstanding welcome delivery. Welcome records are local-only in Bridge V1.

## Domain

`assistants` owns teams, assistants, scoped memories and assignments/messages. V1 assistants belong to one team. Details uses the desktop Select to change membership within the account. Private notes follow the assistant in the same transaction and advance their revisions; shared team memories, historical assignments and chats remain intact. A move waits until running conversations, open assignments, unsettled deliveries and generating/starting welcomes finish. Assignment admission rechecks membership after asynchronous execution resolution. Teams share knowledge across Developer and Work runs without turning a Collection into a git project. Run execution, provider sessions, history, approvals and artifacts remain in `runs`. References to runs do not create a second transcript.

Memories are individual or team-scoped, bounded, revision checked, and attributed to a user or source run. Important facts are pinned; a turn receives pinned and relevant records plus its team's roster. Authorized history reads use existing run history. Assignment status/results are separate from memory.

Assignments store the requesting run, target assistant, task key, parent, worker run, state, result and evidence. A durable message queue owns dispatch. Repeating a task key returns the original assignment. A worker uses its own assistant's frozen settings and permissions; delegation never inherits greater permissions from the requester. Same-workspace work is serialized. Cycles and excessive depth are rejected.

## Lifecycle

Queue delivery is `queued -> dispatching -> delivered`, or `uncertain` after a crash/dispatched failure. Commit a delivery claim and its preallocated run identity before starting provider effects. Recovery reconciles the stored run instead of repeating an uncertain action. Accepted but not yet dispatched work can retry. Stop closes admission and joins pending dispatch before database release. Closing the page does not stop work.

Assignment states are queued, running, blocked, uncertain, completed, failed and canceled. Provider turn completion does not prove task completion: workers report a result and evidence explicitly. Completion creates an idempotent result delivery back to the requester. A result contains reference data, never new authorization. Stopping a chat stops its current turn; incoming reports stay visible in assignments without restarting a canceled requester. Canceling an assignment also cancels its queued messages.

## Implementation / acceptance

1. Shared contracts, migration, profile validation and frozen run integration.
2. Scoped memory and per-turn context; own/authorized team conversation reads.
3. Durable assignment/message dispatch, result delivery, bounded delegation and restart reconciliation.
4. Assistants sidebar, creation page and ordinary conversation pane. Team memory, assignments and profile live in the right information panel. Reuse existing run history, stream reconciliation, rich composer and approval UI.
5. Backend lifecycle/IPC for desktop and standalone; typed renderer transport.
6. SQLite integration tests for profile freezing, account/team boundaries, memory conflicts, task deduplication, delegation loops, restart and shutdown; renderer typecheck and build.

V1 is local to the owning backend, accessible through desktop and authenticated web transport. Bridge replication, mobile-specific screens, scheduled/proactive assignments and execution-profile handoff are later work. New local tables are deliberately excluded from Bridge's replicated table manifest.
